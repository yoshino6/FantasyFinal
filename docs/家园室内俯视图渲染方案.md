# 家园室内俯视图与自动布置方案

> 状态：评审稿，不生成图片、不修改当前运行逻辑。
>
> 目标：让玩家在 `/家园` 中查看自己的小屋俯视图。画面包含墙壁、地板、房间背景与已制作家具；一层、二层、三层分别保存并显示。家具使用固定贴图与固定占格，由服务端自动布置，保证不重叠、不越界、遵守数量上限。

## 1. 范围与原则

### 1.1 本期要实现

- 每个拥有小屋的角色可查看独立的室内俯视图；
- 房屋为正方形房间，随房屋等级提高而扩大；
- 每层独立渲染、独立保存家具位置；
- 墙壁、地板、门、阴影和家具全部来自固定素材；
- 制作家具后由服务端选出一个合法位置并落库；
- 已放入的家具不会因后续摆放而被重新洗牌；
- 玩家切换楼层时只查看该楼层，不能看到他人的家园画面；
- 家园面板继续使用现有 Markdown、引用文本、蓝色按钮；图片作为附加内容发送。

### 1.2 明确不做

- 不使用 AI 每次实时生成房间或家具图；
- 不开放自由拖拽、旋转和访客参观；
- 不把图片当成唯一真实数据：家具位置、占格和限制仍以数据库为准；
- 不为每个玩家复制一套原始 PNG 素材，只缓存最终合成图。

固定贴图的好处是视觉稳定、可审核、缓存命中率高，也避免生成结果与实际家具数量不一致。

## 2. 视觉规格

### 2.1 房间尺寸与格子

采用「逻辑格子 + 固定像素」方案。逻辑格子负责判定，贴图只负责显示。

| 房屋等级 | 房间逻辑尺寸 | 可摆放内区 | 输出图尺寸 | 单格像素 | 每层槽位上限（沿用现有） |
| --- | ---: | ---: | ---: | ---: | ---: |
| Lv.1 简陋木屋 | 12 × 12 | 10 × 10 | 768 × 768 px | 48 px | 6 |
| Lv.2 扩建木屋 | 16 × 16 | 14 × 14 | 960 × 960 px | 48 px | 8 |
| Lv.3 多层宅邸 | 20 × 20 | 18 × 18 | 1152 × 1152 px | 48 px | 10 |

- 最外圈一格是不可摆放的墙壁与阴影区；
- 可摆放内区坐标从 `(1, 1)` 开始，左上角为原点，`x` 向右、`y` 向下；
- 门固定在下墙居中位置，占用墙体区域，不允许家具覆盖；
- 二层、三层与一层使用同样尺寸规则；房屋等级决定所有已扩建楼层的尺寸；
- 同一家具的像素贴图会按其占格尺寸输出，不允许运行时任意拉伸变形。

### 2.2 分层绘制顺序

最终成品图按以下顺序合成：

```text
房间背景（墙外暗角）
  └─ 墙体、门、窗、楼梯口
      └─ 地板纹理与地毯底层
          └─ 家具投影
              └─ 家具主体贴图
                  └─ 环境光、楼层标签、轻量装饰
```

这样地毯能够在家具下方，床、储物箱和训练木桩有稳定投影，墙体也不会被家具遮挡。

### 2.3 楼层表现

| 楼层 | 标记 | 固定环境差异 | 说明 |
| --- | --- | --- | --- |
| 一层 | `一层` | 正门、窗户、默认暖色木地板 | 入口层，优先显示床、储物箱与训练木桩 |
| 二层 | `二层` | 楼梯口、侧窗、较亮地板 | 扩建二层后显示；楼梯口不可摆放 |
| 三层 | `三层` | 天窗、深色墙边、月光叠层 | 扩建三层后显示；月光灯视觉效果最明显 |

楼层差异应来自各自的背景层，而不是对同一背景图强行换色。

素材建议由美术一次性导出为透明 WebP（优先）或 PNG。使用 2 倍分辨率源图，在服务端缩放到显示尺寸，可避免聊天平台压缩后锯齿明显。

## 4. 数据结构调整

当前 `player_home_furniture.slot_key` 只表达逻辑槽位，不能保证矩形家具不会碰撞。室内图落地时，需要把「家具实例」与「占用格」持久化。

### 4.1 家具定义增加占格与自动布置策略

```sql
ALTER TABLE home_furniture_definitions
  ADD COLUMN grid_width TINYINT UNSIGNED NOT NULL DEFAULT 1,
  ADD COLUMN grid_height TINYINT UNSIGNED NOT NULL DEFAULT 1,
  ADD COLUMN placement_rule ENUM('wall','center','corner','wall_or_center') NOT NULL DEFAULT 'wall_or_center',
  ADD COLUMN layer_order SMALLINT NOT NULL DEFAULT 20;
```

建议种子值：

```text
床 / 陈列架 / 暖炉 / 储物箱：placement_rule=wall
训练木桩：placement_rule=center
幽狼皮毯：placement_rule=center，layer_order=10
月光灯：placement_rule=corner
其他家具：placement_rule=wall_or_center
```

### 4.2 家具实例增加最终布局位置

```sql
ALTER TABLE player_home_furniture
  ADD COLUMN grid_x TINYINT UNSIGNED NULL,
  ADD COLUMN grid_y TINYINT UNSIGNED NULL,
  ADD COLUMN rotation TINYINT UNSIGNED NOT NULL DEFAULT 0,
  ADD COLUMN layout_version SMALLINT UNSIGNED NOT NULL DEFAULT 1;
```

`grid_x/grid_y` 是家具左上角占格。v1 固定贴图不旋转，`rotation` 先固定为 `0`，但预留字段可避免将来扩展时改表。

### 4.3 以占格表做数据库级防重叠

仅用应用层判断会在并发制作时产生重叠风险。新增占格表，以唯一键作为最终防线：

```sql
CREATE TABLE IF NOT EXISTS player_home_furniture_cells (
  home_id BIGINT UNSIGNED NOT NULL,
  floor_no TINYINT UNSIGNED NOT NULL,
  grid_x TINYINT UNSIGNED NOT NULL,
  grid_y TINYINT UNSIGNED NOT NULL,
  furniture_id BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (home_id, floor_no, grid_x, grid_y),
  KEY idx_home_furniture_cell_instance (furniture_id),
  CONSTRAINT fk_home_cell_furniture
    FOREIGN KEY (furniture_id) REFERENCES player_home_furniture(id) ON DELETE CASCADE
) ENGINE=InnoDB;
```

当一张 3×4 的床落在 `(2, 1)` 时，服务端写入 12 行格子记录；若任何一行和已有家具冲突，唯一键会拒绝整笔事务。

### 4.4 渲染缓存表

```sql
CREATE TABLE IF NOT EXISTS player_home_floor_renders (
  home_id BIGINT UNSIGNED NOT NULL,
  floor_no TINYINT UNSIGNED NOT NULL,
  layout_hash CHAR(64) NOT NULL,
  image_path VARCHAR(255) NOT NULL,
  rendered_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (home_id, floor_no),
  CONSTRAINT fk_home_render_home
    FOREIGN KEY (home_id) REFERENCES player_homes(id) ON DELETE CASCADE
) ENGINE=InnoDB;
```

`layout_hash` 由房屋等级、楼层、背景版本、家具代码、坐标、素材版本共同计算。哈希未变则直接复用旧图。

## 5. 自动布置规则

### 5.1 关键原则

1. 家具制作成功后即确定位置并落库；以后浏览只读位置，不重新随机。
2. 先校验家园等级、楼层、每层数量限制和现有槽位限制，再尝试占格。
3. 每个候选位置均检查：在可摆放内区、未占用、未覆盖门/楼梯/窗保留区、满足家具规则。
4. 写入家具实例与格子占用必须使用同一个 `withTransaction`。
5. 如果不存在合法位置，整个制作事务回滚，材料不扣除，提示“本层没有可放置该家具的空间”。

### 5.2 固定候选顺序

候选顺序不是纯随机。使用可解释、稳定且符合直觉的优先级：

```text
wall：上墙 → 左墙 → 右墙 → 下墙；每段从角落向中央扫描
corner：左上 → 右上 → 左下 → 右下
center：中央 4×4 区 → 向外螺旋扫描
wall_or_center：先 wall，再 center
```

每类内部以稳定哈希 `sha256(homeId:floorNo:furnitureId)` 决定起始偏移。这样不同玩家的小屋不会永远完全一致，同一玩家在重启后仍得到同样的结果。

### 5.3 特殊避让规则

| 家具 | 额外规则 |
| --- | --- |
| 床 | 必须有一条长边贴墙；床头不能贴门或楼梯口 |
| 暖炉 | 必须贴墙；与床之间至少保留 1 格 |
| 储物箱 / 陈列架 | 必须贴墙；不遮挡门前 2 格通道 |
| 训练木桩 | 周围 1 格必须为空，形成训练空地 |
| 地毯 | 可被床、木桩、箱子压住；它只与其他地毯互斥 |
| 月光灯 | 仅放四角或窗边指定锚点，不占家具通路 |

地毯是唯一的低层家具：渲染时允许其他家具盖在它上面；逻辑上仍应避免两张地毯完全重叠。

### 5.4 伪代码

```ts
for (const candidate of candidatesFor(definition, room, stableSeed)) {
  const cells = rectangle(candidate.x, candidate.y, definition.gridWidth, definition.gridHeight);
  if (!insideInnerRoom(cells, room)) continue;
  if (hitsReservedCells(cells, room)) continue;
  if (!matchesPlacementRule(candidate, definition, room)) continue;
  if (!satisfiesClearance(cells, definition, occupiedCells)) continue;
  if (collidesWithFurniture(cells, occupiedCells, definition.layerOrder)) continue;
  return candidate;
}
throw new Error('本层没有可放置该家具的空间。');
```

现有旧家具没有坐标时，第一次升级到本系统应按 `placed_at,id` 顺序补排；如果补排失败，不删除家具，而是标记为“待重新布置”，由管理员或后续整理命令处理。

## 6. 图片合成实现

### 6.1 建议模块

```text
src/game/home-layout.service.ts   # 房间尺寸、保留格、候选扫描、占格写入
src/game/home-render.service.ts   # Sharp 合成、缓存哈希、清理旧缓存
src/response/home.ts              # 在家园面板中发送当前楼层图片
src/response/home-layout.ts       # 可选：单独的“布置与楼层”面板
src/assets/home/**                # 编译期直接导入的固定背景与家具贴图
```

项目已经依赖 `sharp`，渲染服务直接用其 `composite()` 合成，无需增加绘图库。默认素材应以直接 import 的方式交给构建链路；最终缓存图可存放在 `.data/qq-bot/home-renders/`，按 `homeId/floor/layoutHash.webp` 命名。

### 6.2 合成流程

```text
读取 home + floor + 家具实例 + 当前素材版本
  → 计算 layout_hash
  → 命中缓存：返回已有图片
  → 未命中：加载该等级/楼层的背景
  → 按 layer_order、grid_y、grid_x 排序家具
  → 计算像素坐标：px = grid_x × 48，py = grid_y × 48
  → 叠加阴影和家具贴图
  → 叠加“第 N 层 / 房屋 Lv.N”小标签
  → 输出 WebP 并写缓存表
  → 通过 Format 图片组件发送
```

建议 WebP 质量 `82`、无损关闭、大小控制在 1 MB 内。若平台不支持图片发送，回退到当前文字家园面板，不影响任何业务操作。

### 6.3 触发与失效

| 事件 | 处理 |
| --- | --- |
| 第一次打开 `/家园楼层 N` | 若无缓存则同步渲染 |
| 制作家具成功 | 清除该楼层缓存，返回最新成品图 |
| 拆除家具成功 | 清除该楼层缓存，返回最新成品图 |
| 房屋升级 | 清除所有已开放楼层缓存，背景和可摆放尺寸更新 |
| 扩建楼层 | 首次打开该层时生成空房间背景 |
| 更换任意素材 | 提升 `HOME_ASSET_VERSION`，使布局哈希自然失效 |

渲染不应在每次 `/家园` 都阻塞；只在需要图片时渲染，且缓存命中时只读取文件。

## 8. 事务、权限与安全

- 仅房主可读取自己的 `player_home_floor_renders`；图片 URL 或本地文件路径不能由客户端传入；
- 制作、拆除、升级、扩建一律锁定 `player_homes`、对应楼层的 `player_home_furniture_cells` 和材料行；
- 先找到位置、写家具实例、写所有格子、扣材料，再提交事务；任一步失败均回滚；
- 缓存图是可再生数据，文件丢失时由布局表重新渲染；
- 文件路径必须由服务端根据 `home_id/floor/hash` 生成，禁止拼接用户输入；
- 同一用户同时点击两次制作，第二个事务因格子唯一键或家具限制失败，不会得到重叠家具。

## 9. 实施阶段与验收

### 阶段 A：数据与布局（无美术也可测试）

1. 新增占格字段、占格表、缓存表与家具定义字段；
2. 为现有 8 种家具写入尺寸、规则、图层；
3. 抽出 `home-layout.service.ts`，制作时自动寻址并写占格；
4. 用纯色调试块替代贴图，验证位置、边界和重叠。

验收：连续制作床、箱子、木桩、地毯后，数据库中无重复 `(home_id,floor_no,grid_x,grid_y)`，所有矩形都在可摆放内区。

### 阶段 B：素材与渲染

1. 美术按第 3 节提供 6 张房间背景、8 张家具贴图和阴影素材；
2. 实现 `home-render.service.ts` 与 WebP 缓存；
3. 在 `/家园楼层` 返回图片和文字面板；
4. 在制作/拆除后主动刷新当前楼层。

验收：一、二、三层分别显示正确背景；床贴墙、地毯在底层、灯具在角落；缓存命中时不重新合成。

### 阶段 C：回归与性能

1. 并发制作、材料不足、满房间、未扩建楼层、缓存文件被删除；
2. 大量玩家同时查看不同家园；
3. 图片发送失败时回退文字面板；
4. 统计渲染耗时、文件大小、缓存命中率。

建议指标：冷渲染小于 500 ms、缓存读取小于 80 ms、单图小于 1 MB；若峰值时渲染压力大，再加入按 `home_id:floor` 的短时任务去重。

## 10. 需要评估确认的选项

1. **房屋尺寸**：是否接受 Lv.1/2/3 为 12/16/20 格？它能明显体现升级空间，又不会让单图过大。
2. **自动布置稳定性**：推荐“新增家具只找空位，不挪旧家具”；是否需要后续加入玩家确认后的“一键整理”？
3. **贴图风格**：推荐像素风俯视 3/4 视角，暖木屋基调，家具边缘带一像素深色描边，便于聊天窗口辨认。
4. **楼层入口**：推荐 `/家园` 只显示概览，`/家园楼层 N` 才发送图片，避免每次操作都上传大图。

确认本方案后，再进入素材生成与代码实现阶段。
