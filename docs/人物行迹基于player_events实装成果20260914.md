# 人物行迹基于 `player_events` 的实装成果（2026-09-14）

## 当前结论

已按指定方案扩展现有 `player_events`，人物有效操作的事实、来源、六维倾向和积分使用同一事件 ID；没有新增 `character_operation_facts`。下表列出的真实业务结算点已接入，**仍不能宣称“人物所有有效操作”全量覆盖**。数据库迁移、服务重启、真实角色操作与历史数据回填未在本地执行。

## 总账与查询

| 项目 | 本次实现 |
| --- | --- |
| 事实表 | `player_events` 保留旧 `player_id,event_type,payload,created_at` 语义，增加 `character_id`、业务来源与来源哈希、角色来源、父事件、结果摘要、六维权重、原始及有效积分、六维变动、业务日期、映射状态、毫秒时间与查询索引。旧写入代码继续可用，旧行保持 `legacy`。 |
| 旧事件复用 | 创建角色、社交和已有家园事件、进化之种觉醒在原事件行补齐元数据，并合并安全详情快照，不另造同类型重复事件。 |
| 育成账 | `character_tendency_balances` 保存六维累计／已用／质变占位与版本；`character_tendency_changes` 以 `player_events.id` 关联每笔实得积分。未映射、系统、管理员、零档、同源重复和达日限的结果仍保留事实，实得积分为 0。 |
| 幂等与抗刷 | 同角色的业务来源哈希唯一；积分在业务事务内入账，同一来源重复提交只返回旧事件。评分采用 0.1 点整数单位、按六维权重守恒分配；已接入类型可配置每日上限与同目标重复间隔。 |
| 玩家查询 | `/行迹 [游标]` 分页，`/行迹详情 <编号>` 按角色归属读单笔详情，`/育成` 查看六维积分；详情展示来源、结果、倾向与实际积分原因。只读查询不产生日志或积分。 |

## 尚未完成的覆盖与发布门槛

- 最新静态扫描：`src/game` 有 77 个文件含 `withTransaction`，其中 14 个文件没有直接调用记录函数。管理／权限／测试／账号注销、注册前接引展示可排除；`alchemy-journal` 与 `automaton-construction` 委托上层的工艺结算点，`home-render` 是渲染缓存。这个文件数**不能证明业务分支全覆盖**，仍需按设计文档逐项建立“业务结果 → 类型 → 来源 → 详情 → 测试”的验收清单。
- 仍需逐结算点核对其余剧情分支、探索首次发现、部分服务内的派生收益与 NPC 状态变化；进化定型的选择目前是尚可反复修改的草案，最终定型已随注射结算记录。不能把原有成就或天赋日志自动算作人物行迹。`player_events` 旧行和注册前事件尚未按角色全量回填。
- 尚未建立所有入口的逐项覆盖测试；本地仅有记录服务 mock 测试，不能证明全部按钮／文本入口、业务回滚及并发路径均正确。队伍个人贡献、跨玩法同源去重和积分实际频率回放尚未完成。
- 目前的六维权重和积分是首轮暂定规则；组队个人贡献摘要、跨玩法同源去重及实际频率回放尚未完成。余额只开放记录与查询，**质变兑换暂未开放**，避免未经回放的数值永久进入基础六维。
- 旧 `player_events` 行未批量补历史角色归属，玩家行迹查询只展示本次按 `mapped/unmapped` 新格式写入的记录。后续历史回填需要先审计旧事件类型与角色归属。
- 需在目标数据库实际执行迁移，并用真实服务路径核对“业务状态 → 事件行 → 六维变动 → 余额 → 角色属性”、重复回调、回滚、并发与其他角色不可见；本地测试不能代替上线验收。待接入项未清零前不得宣称全量完成。
