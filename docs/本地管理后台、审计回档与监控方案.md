# 本地管理后台、审计回档与监控方案

> 状态：第一阶段已落地；公网部署、全量玩家操作审计与回档仍按下方清单继续实施。  
> 目标：在 FantasyFinal 现有 AlemonJS + Koa + MySQL 架构内，提供可安全部署到公网的网页管理后台：主人使用固定账号 `admin` 与已设置的密码登录，并可创建、禁用和管理其他管理员账号；后台用于查询玩家和世界、执行受控管理操作、完整追溯操作链，并在异常发生前后给出可行动的告警。

## 1. 方案结论

建议把后台作为**当前机器人 HTTP 服务中的受保护 Koa 子路由**实现，而不是新开一套独立服务或引入新的 Web 框架。

```text
公网浏览器
    │ HTTPS :443（独立管理域名）
    ▼
Caddy / Nginx 反向代理
    ├─ 自动续期 TLS 证书、HSTS、请求体与速率限制
    └─ 仅转发到服务器本机的 Node 监听端口
                    │ 127.0.0.1
                    ▼
AlemonJS 当前 HTTP 服务（已有 koaRouter）
    ├─ /admin                 管理后台单页入口
    └─ /api/admin/*           受会话、CSRF、角色、限流保护的 JSON API
             │
             ├─ 查询服务       玩家、世界、日志、监控快照
             ├─ 受控命令服务   复用现有游戏 service，不允许后台直拼 SQL 修改业务状态
             ├─ 操作总账       追加式 operation_journals + 快照 + 回滚链
             └─ 监控服务       任务心跳、健康检查、异常规则、告警记录
                         │
                         ▼
                   现有 MySQL 游戏库
```

这样可直接复用项目现有的 `getPool`、`withTransaction`、管理员权限、`admin_operation_logs`、`player_events`、`game_event_ledger`、世界生态快照和系统状态快照；不会复制一份游戏规则到网页端。网页只负责展示、筛选、提交受校验的管理意图，所有真正的数据变更仍落在 service 层事务中。

本方案的核心边界如下：

1. 公网只暴露反向代理的 HTTPS `443`（及证书校验所需端口）；Node 后台端口、MySQL、Redis 和管理探针仅监听/放行服务器本机或私有网络，绝不直接暴露。
2. 查询与修改严格分离。页面访问、筛选和导出不改变数据；任何写入都必须经过权限、预览、原因、二次确认、事务和审计。
3. 不提供任意 SQL、任意 JSON 覆盖或“直接改表”能力。每种可写操作都必须有明确输入、范围、校验、前后快照和可回退规则。
4. “回档”不是回滚整个数据库。它是针对一笔可证明、可隔离、无后续冲突的操作执行补偿或恢复快照；全库灾难恢复仍依赖 MySQL 备份和二进制日志。
5. 监控只自动发现、记录和告警；除既有安全幂等补偿外，不让监控静默改动玩家或世界数据。
6. 固定主人账号为 `admin`，它是唯一不可降级、不可删除、不可禁用的 `owner`；主人可在网页内创建与管理普通管理员账号。

## 2. 现有基础与缺口

| 现有能力 | 可直接复用 | 当前缺口 |
| --- | --- | --- |
| HTTP | `src/index.ts` 已注册 `koaRouter`，已有 `/api/ping` | 只有演示接口，没有后台登录、静态页、权限或 API 规范 |
| 玩家数据 | `players`、`characters`、背包/装备、技能、任务、进化、社交、家园、市场等已有实体 | 没有统一的玩家聚合查询与安全编辑入口 |
| 玩家事件 | `player_events` 已记录注册、进化、家园和部分社交事件 | 覆盖范围是局部的，不能证明“每一个具体操作”都被记录，也没有通用前后快照或回滚关联 |
| 世界事件 | `game_event_ledger` 和 `worldAdminSnapshot()` 已覆盖天气、奇遇、世界线、NPC、站点和首领门 | 仅覆盖动态世界领域，不覆盖所有地图生态、管理变更和任务健康 |
| 管理记录 | `admin_operation_logs`、`recordAdminOperation()` 已记录许多机器人管理命令 | 记录是短文本，不含请求来源、变更差异、确认链、失败态和可恢复快照 |
| 数据修复 | `admin-audit.service.ts` 已有角色、背包、技能、状态核查；注销账号已有快照恢复 | 缺少网页预览、统一风险分级、一次操作一条完整证据链，以及跨功能的安全回退机制 |
| 状态查询 | `systemStatusSnapshot()` 已能读取进程、内存、磁盘、数据库可用时的游戏数量摘要 | 没有任务成功/失败心跳、阈值规则、告警生命周期和历史趋势 |

因此不能把旧的 `player_events` 或管理文本日志硬改成“全量审计日志”。应保留它们的现有职责，新增一个面向管理与回溯的统一操作总账，并渐进式将所有可变玩家操作纳入其中。

## 3. 公网部署、登录与权限

### 3.1 网络边界与 HTTPS

- 使用独立域名（例如 `admin.<游戏域名>`）承载后台，DNS 指向服务器；浏览器到反向代理的流量始终使用 HTTPS，HTTP 仅做 301 跳转或证书校验。
- 推荐由 Caddy 或 Nginx 终止 TLS、自动续期证书、强制 HTTPS 与 HSTS；反向代理只把后台流量转发给 `127.0.0.1` 上的 AlemonJS/Koa 服务。服务器防火墙只允许公网访问 `80/443`，不开放 Node、MySQL 和 Redis 的业务端口。
- 默认路由为 `/admin` 和 `/api/admin/*`，与玩家命令和普通 `/api` 路由隔离；后台 API 仅接受正确 Host、HTTPS 协议和预期的管理域名。
- 应用只在连接来自配置的反向代理地址时读取 `X-Forwarded-For`、`X-Forwarded-Proto`；任何直连请求均不信任这些头。不得用无条件的 `trust proxy=true` 伪造客户端 IP 或 HTTPS 状态。
- 反向代理与应用均设定请求体上限、请求超时、登录/确认接口限流；应用增加 CSP、`frame-ancestors 'none'`、`X-Content-Type-Options: nosniff` 和严格 Referrer Policy，防止点击劫持与资源注入。
- 页面和 API 统一设置 `Cache-Control: no-store`；错误页和日志接口不得输出数据库密码、会话令牌、完整堆栈或原始敏感载荷。

### 3.2 管理员账号与角色

新增独立的网页后台账号，而不把浏览器身份伪装成 QQ 用户。机器人端 `game_permissions` 继续服务于 QQ 命令；网页端使用可审计的 `admin_web_accounts`。公网后台的主人账号固定为小写 `admin`：首次部署由已设置的 owner 密码哈希引导创建，之后始终以 `admin + 密码` 登录。

| 角色 | 可做的事 | 明确禁止 |
| --- | --- | --- |
| `viewer` | 全部只读页面、筛选、受脱敏限制的导出 | 任何修改、导出完整快照、查看安全风险细节 |
| `admin` | 常规玩家核查、受白名单限制的修复、世界内容启停/权重、查看操作总账 | 权限管理、全服破坏性操作、强制快照恢复、监控规则与备份策略修改 |
| `owner`（固定账号 `admin`） | 全部能力，包括创建/禁用/重置管理员账号、角色、风险操作、回档确认和安全配置 | 不受审计约束；owner 自己的操作同样必须记录 |

- 密码只保存为 Node 内置 `scrypt` 生成的加盐哈希，绝不写入源码、浏览器存储、普通日志或审计快照。
- 将当前源码中的主人密码配置迁移为集中、可校验的 `FantasyFinal.adminWeb` 配置；`admin` 的初始化密码只接受密码哈希，不再让网页或机器人依赖明文密码。数据库中已存在 `admin` 时，启动不得用配置覆盖其已变更的密码。
- 主人可在“管理员账号”页创建 `admin` 角色账号、设置初始密码、强制下次登录改密、禁用账号、重置密码和撤销所有会话；普通管理员不能创建管理员、提升权限、操作 owner 或重置其他账号密码。`admin` 账号不可改名、降级、删除或禁用。
- 登录成功后创建随机、不透明、只存哈希的会话；公网 Cookie 始终使用 `Secure`、`HttpOnly`、`SameSite=Strict`，会话绝对过期与空闲过期均受配置控制。管理员被禁用、改密或重置密码时，其全部会话立即撤销。
- 所有写接口要求同源校验与 CSRF Token；登录、确认、回档和权限管理额外按账号、来源 IP 与会话限流。连续失败会写安全告警，响应始终使用统一的“账号或密码错误”，不暴露账号存在性。
- 建议公网正式服为 owner 及高风险确认启用 TOTP 二次验证和近期重新输入密码；若暂不启用，后台首页应显著显示安全降级警告，并禁止关闭该警告的记录。

建议配置结构（不在文档或源码中填写真实密码）：

```yaml
FantasyFinal:
  adminWeb:
    enabled: true
    path: /admin
    publicBaseUrl: "https://admin.example.com"
    trustedProxyIps: ["127.0.0.1", "::1"]
    sessionIdleMinutes: 30
    sessionAbsoluteMinutes: 480
    ownerUsername: "admin"
    ownerBootstrapPasswordHash: "scrypt$..."
    requireOwnerMfa: true
```

启动时必须校验：后台启用但没有有效的 HTTPS 公网地址、可信代理地址和 `admin` 引导密码哈希时，后台路由不注册；不能以空密码、默认密码、HTTP Cookie 或开发回退模式启动。正式运行后，`ownerBootstrapPasswordHash` 仅在数据库没有 `admin` 账号时使用。

### 3.3 写操作防呆流程

所有写操作统一经过如下状态机：

```text
填写操作与原因
  -> 服务层校验权限、输入、目标当前版本、战斗/旅行等前置状态
  -> 返回只读预览（影响范围、before/after 差异、风险级别、能否回退）
  -> 用户在有效期内二次确认
  -> 同一事务内执行 + 写操作总账 + 写快照
  -> 返回操作编号、结果和回退资格
```

- 低风险：修改可逆的后台展示设置、启停未开始的内容模板。
- 中风险：单个玩家的受控物品/货币补偿、地图移动、状态修复、世界内容权重。
- 高风险：清空背包、关闭地图、重建迷宫、全服操作、注销数据恢复、强制回档。仅 owner 可执行，必须填写原因、输入确认短语，并在执行前建立完整范围快照。
- 预览与确认之间以目标的 `updated_at` / 领域修订号乐观锁定。目标已经变化时确认失败并要求重新预览，禁止拿旧页面覆盖新数据。

## 4. 网页信息架构

### 4.1 导航与首页

```text
总览
├─ 玩家
│  ├─ 玩家列表
│  ├─ 玩家详情（资料 / 资产 / 成长 / 状态 / 关联记录）
│  └─ 玩家操作时间线
├─ 世界
│  ├─ 世界总览
│  ├─ 区域与生态
│  ├─ 动态世界（天气 / 世界线 / NPC / 站点 / 首领门）
│  └─ 地图、Boss、怪物、矿产、迷宫
├─ 审计与回档
│  ├─ 操作总账
│  ├─ 现有玩家事件 / 世界账本 / 管理日志联查
│  └─ 回档预览与执行记录
├─ 监控与告警
│  ├─ 当前健康度
│  ├─ 计划任务心跳
│  ├─ 数据一致性检查
│  └─ 告警历史
└─ 系统与权限（owner）
```

首页不堆放全量数据，只显示：数据库/服务健康、最近失败任务、未确认高危告警、活跃玩家/战斗/旅行、当前世界奇遇与场景数、最近操作和需要人工处理的核查结果。每个指标都可进入带筛选条件的详情页。

### 4.2 玩家列表与筛选

玩家列表以 `players + characters + map_regions` 为主查询，严格分页，不做一次性全表读取。首期支持：

| 维度 | 筛选/排序 |
| --- | --- |
| 身份 | QQ 用户 ID、游戏 ID、角色名、QQ 昵称、账户状态、注册时间 |
| 成长 | 等级区间、境界、冒险者等级、主/副职业、是否已登记冒险者 |
| 所在与活动 | 当前区域、坐标范围、活动状态、是否旅行、是否战斗、最后一次可审计操作时间 |
| 资产与风险 | 铜币区间、背包/装备异常标记、未结算状态、近 24 小时失败操作、风控待审标记 |
| 关系数据 | 公会/队伍、家园、主线阶段、进化档案是否建立 |

默认排序为最近操作时间倒序，其次为角色 ID；支持名称、ID、区域和操作编号全文前缀搜索。大表日志使用 `(created_at, id)` 游标翻页，普通列表限制单页最多 100 条、单次时间范围最多 31 天，避免后台查询反过来拖慢游戏。

### 4.3 玩家详情

玩家详情按需加载，下列分区均只读，除非该区有明确的受控操作按钮：

- **身份与位置**：账户/角色标识、注册与状态、区域与坐标、活动状态、旅行、当前战斗、最近活跃时间。
- **角色面板**：等级、经验、境界、属性、成长、生命/魔力、战斗派生属性、元素属性、职业与技能点。
- **资产**：铜币、背包堆叠物品、装备实例、已装备栏位、快捷栏、锻造/炼金进行项、邮件与市场/委托中的占用资产。
- **进度**：主线、支线、冒险者、公会、地下城、家园、进化档案、变异、图鉴与已知世界线影响。
- **关联状态**：队伍、公会、PvP、悬赏、旅行、战斗、资源采集及有明确生命周期的临时实体。
- **时间线**：新的操作总账优先展示，并可联查旧 `player_events`、世界账本和管理员操作记录。筛选支持时间、动作类型、来源、结果、区域、关联 ID、操作者、风险级别与是否可回退。

首期只开放已有业务语义的管理操作：角色/背包/技能/状态核查、已有的注销记录恢复、明确的物品或货币补偿、取消可安全取消的未开始操作、管理员邮件发放，以及已有世界管理服务中的动作。所有新增编辑都必须先新增对应 service，不能让详情页直接更新 `characters` 或子表。

### 4.4 世界总览与管理

世界页复用 `worldAdminSnapshot()`、`systemStatusSnapshot()`、现有 Boss/怪物/矿产/迷宫管理服务和全局设置服务，分为：

| 页面 | 查询内容 | 首期写入能力 |
| --- | --- | --- |
| 世界总览 | 区域天气、世界线、首领门、巡游 NPC、站点、活跃奇遇/场景、今日世界账本量 | 只读 |
| 区域与地图 | 区域边界、开放状态、玩家/怪物/资源计数、Boss、悬赏、传送/战斗/采集占用 | 按既有规则开放/关闭受管理地图；关闭前必须显示迁移、清理和中断范围 |
| 动态世界 | 天气、世界线阶段、NPC 状态、站点状态、内容模板校验与权重 | 内容启停、权重调整；不允许手写历史实例 JSON |
| 生态实体 | Boss、小怪、矿产、地下迷宫及其活跃/战斗/采集状态 | 复用既有刷新、消灭、悬赏、重建等 service，并增加预览与高风险确认 |
| 全局设置 | 经验、掉落、铜币倍率及其生效范围 | 使用现有校验范围，不新增未定义的全局数值编辑器 |

世界影响的每一笔写入同时写入操作总账和 `game_event_ledger`。已经创建的战斗、奇遇、场景或实例保持创建时快照，后台修改只影响后续生成，除非某项专门的修复服务在预览中列出所有受影响实例。

## 5. 统一审计、快照与回档

### 5.1 三类既有记录的定位

- `player_events`：保留为玩家可见或游戏叙事性的摘要事件；后续可由操作总账生成必要摘要，但不将高频、敏感审计信息全部塞入该表。
- `game_event_ledger`：保留为动态世界的因果账本；以 `correlation_id` 与操作总账关联。
- `admin_operation_logs`：保留已存在 QQ 管理命令的轻量兼容记录；网页端的详细操作改写新总账，并在后台页面中合并展示。

### 5.2 新增数据结构

| 表 | 核心字段 | 用途与索引 |
| --- | --- | --- |
| `admin_web_accounts` | `id`、`username`、`password_hash`、`role`、`is_enabled`、时间字段 | 网页管理员身份；用户名唯一、角色索引 |
| `admin_web_sessions` | `id`、`account_id`、`token_hash`、`csrf_secret_hash`、`ip`、过期/最后活跃/撤销时间 | 不保存明文 token；按 token、过期和账号索引 |
| `admin_web_login_attempts` | 账号摘要、来源 IP 摘要、结果、失败原因类别、`created_at` | 支撑账户/IP 双维度限流与安全告警；保留期受配置控制 |
| `admin_web_mfa_credentials` | `account_id`、加密后的 TOTP 密钥、启用/验证时间、恢复码哈希 | owner 与高风险确认的二次验证；密钥/恢复码不回显也不写审计载荷 |
| `operation_journals` | UUID、`actor_kind`、`actor_ref`、`source`、`action_type`、`status`、`risk_level`、`correlation_id`、原因、请求摘要、结果摘要、开始/结束时间、`rollback_of` | 所有玩家、管理员、系统的可审计操作主表；按目标、操作者、动作、状态、时间、关联 ID 建组合索引 |
| `operation_targets` | `operation_id`、`target_kind`、`target_id`、`player_id`、`character_id`、`region_id` | 一笔操作可关联多玩家、多实体；支持时间线与反向筛选 |
| `operation_snapshots` | `operation_id`、`scope`、`schema_version`、`before_json`、`after_json`、`before_hash`、`after_hash` | 仅存白名单领域快照；保存哈希用于篡改/冲突检测 |
| `scheduled_job_runs` | `job_code`、运行编号、状态、开始/结束、耗时、错误摘要、影响数 | 所有 cron/interval 的心跳与失败趋势 |
| `monitor_alerts` | 规则、等级、指纹、状态、首次/最近发生、确认人、详情摘要 | 告警去重、确认、恢复与历史查询 |

不在日志中记录后台密码、Cookie/CSRF、数据库配置、完整聊天文本或无必要的隐私标识。快照里的敏感平台字段最小化存储；展示与导出按角色再脱敏。

### 5.3 记录每一个玩家具体操作的方法

新建 `operation-journal.service.ts`，为业务服务提供统一的事务内包装器：

```text
开始操作（生成 correlation_id）
  -> 读取本操作声明的领域快照
  -> 执行既有游戏 service
  -> 读取 after 快照、校验领域不变量
  -> 在同一数据库事务写 committed 总账、目标和快照
  -> 提交
失败：回滚业务事务；另写不含敏感数据的 failed 总账
```

- 玩家从机器人命令触发的**有状态操作**、网页管理员替玩家执行的操作、定时任务对玩家产生的结算，都使用同一操作编号和来源字段。
- 纯读取（例如查看角色、地图、帮助）默认不写玩家业务操作；网页安全日志可独立记录登录、拒绝访问和高风险阅读，避免把无意义浏览污染时间线。
- 先覆盖高风险和高价值领域：注册、移动/旅行结算、战斗结算、掉落与消耗、背包与装备、货币、锻造/炼金、交易、邮件领取/发放、技能、任务/进化、家园、公会/队伍、PvP、账号注销/恢复。
- 每新增或修改一个可改变状态的 handler/service，都必须在测试中验证“成功一条 committed；业务失败一条 failed 且无 after 变更；重复提交不产生第二次结算”。这是以后保持“每个操作都有记录”的门禁，而不是一次性人工约定。
- 已经发生的旧操作不会伪造历史；旧表数据以“历史来源”方式联查。新总账启用后的覆盖率和未接入动作会在监控页显式显示。

### 5.4 快照范围与回档规则

快照按操作声明的领域采集，例如：

| 操作 | 必要快照 | 可回退条件 |
| --- | --- | --- |
| 单人货币/物品补偿 | 货币、相关背包条目、装备实例、物品账本 | 目标条目 after 哈希仍匹配，未被后续消耗/交易/装备影响 |
| 角色状态修复/传送 | 角色状态、旅行、战斗成员、相关位置占用 | 不在活跃战斗、无进行中旅行，当前位置未被后续操作改写 |
| 技能/进化修复 | 技能、技能点账本、进化/变异相关表 | 无后续技能/进化操作，派生属性重算预览通过 |
| 世界内容权重/启停 | 该模板的配置和修订号 | 未有新的同模板配置操作；不影响已创建实例 |
| 地图关闭、迷宫重建、全服操作 | 受影响实体清单和范围快照，另要求数据库备份点 | 默认不提供一键回档；只允许 owner 在预览后执行专门补偿方案 |

回档流程：选择已提交操作 -> 检查操作者权限与回退资格 -> 比较当前版本/after 哈希 -> 展示将恢复与无法恢复的字段 -> owner 填写原因并二次确认 -> 单事务恢复或执行专门补偿 -> 写一笔新的 `rollback` 操作，`rollback_of` 指向原操作。原操作及其快照永不覆盖或删除。

以下情况必须拒绝自动回档并转为人工补偿方案：涉及多玩家交易/PvP、已进入或结束的战斗、已被后续消费的物品、世界全局阶段、不可逆随机结果、跨域联动及任何无法证明没有后续依赖的操作。

### 5.5 数据库备份是独立安全线

操作快照只能处理单笔、白名单范围内的误操作，不能替代备份。上线前需配置：每日逻辑备份、可验证的恢复演练、保留策略、备份失败告警；如需要精确时点恢复，再启用 MySQL binlog 并验证恢复流程。后台的高风险全局操作在执行前要显示最近成功备份时间；备份过期则阻止执行。

## 6. 监控与异常防护

### 6.1 采集方式

在现有 `onReady()` 的 `setInterval` / `setCron` 调度外加一层 `runMonitoredJob(jobCode, action)`：每一次开始、成功、失败、耗时和影响数量均写入 `scheduled_job_runs`，原有任务的业务顺序不改变。`systemStatusSnapshot()` 继续承担机器与游戏数量概览，后台监控服务将其和任务心跳、数据库检查组合为一次健康快照。

### 6.2 首期规则

| 类别 | 监控项 | 告警/处理原则 |
| --- | --- | --- |
| 服务 | HTTP 探针、进程运行时间、内存/RSS、事件循环延迟、磁盘余量 | 高于阈值告警；磁盘和内存临界时停止高风险后台导出，不自动删除数据 |
| 数据库 | 连接/简单查询延迟、连接池等待、事务失败/死锁重试、查询超时 | 连续失败为严重告警；记录错误摘要，不记录凭据与完整 SQL 参数 |
| 调度 | 移动补偿、战斗超时、十分钟动态世界、整点商店/悬赏/迷宫/Boss/生态刷新最后成功时间、连续失败次数、耗时 | 一次失败警告，连续失败或超过两倍周期未成功升级严重告警 |
| 游戏积压 | 到期旅行未结算、过期活跃战斗、卡住采集、异常活跃场景、待处理核查数 | 只列出数量与可定位操作；仍由既有安全结算或管理员修复服务处理 |
| 数据完整性 | HP/MP 越界、无效背包数量、无效快捷栏、重复/失效装备、孤立外键、地图关闭后遗留角色/生态 | 复用现有核查并增加只读扫描；修复前先产生预览与审计 |
| 审计完整性 | 可变操作没有 committed/failed 总账、快照哈希不一致、操作写入失败 | 严重告警并阻止相关高风险写入口，不能继续“无日志运行” |
| 安全 | TLS 证书即将过期、非 HTTPS/错误 Host、直连 Node 端口、伪造代理头、登录失败突增、CSRF/同源拒绝、越权操作、会话异常 | 记录脱敏指纹、限流、在后台突出显示；默认不影响正常玩家游戏 |

阈值以配置项管理，第一周先收集基线再启用提醒级阈值，避免照搬固定数字导致误报。严重告警可在网页实时显著显示；是否向 QQ 主人推送严重告警，应在实施前确定目标账号和限频策略，避免把告警发送到不该接收的群或用户。

### 6.3 告警生命周期与可观测性

每种告警以稳定指纹去重：首次出现创建 `open`，持续发生仅更新计数和最近时间，人工确认标记 `acknowledged`，检查恢复后标记 `resolved`。任何确认、静音和阈值修改也进入操作总账。仪表板保留健康趋势、最近失败任务、警告到严重的升级原因和跳转到关联操作/玩家/世界实体的链接。

## 8. 分期实施

### 阶段 A：只读、安全底座

1. 建立后台配置、loopback 中间件、网页账号、会话、CSRF、限流与统一 API 错误格式。
2. 建表操作总账、目标、快照、任务运行与告警；只初始化，不修改历史玩家数据。

### 阶段 B：操作总账与高风险领域覆盖

1. 实现事务内操作包装器、玩家/世界领域快照和审计覆盖检查。
2. 优先接入注册、移动/旅行结算、战斗结算、掉落/消耗、物品/货币、管理员邮件、背包/装备核查、技能/进化、账号注销/恢复。

4. 后台开放已有安全操作的“预览 -> 确认 -> 执行”，默认先不开放任意字段编辑。

验收：每一个已接入可变操作都能查到来源、操作者、目标、时间、输入摘要、结果、前后差异和关联 ID；失败不会留下部分业务数据；重复请求满足幂等约束。

### 阶段 C：受控编辑与单笔回退

1. 依次开放明确业务语义的单玩家补偿、位置/状态修复、物品/货币调整、内容模板启停/权重调整。

验收：过期预览、目标已变化、正在战斗/旅行、后续已消费、跨玩家关联等情况都被可靠拒绝；成功回退形成新的可追溯操作而不篡改原日志。

### 阶段 D：监控闭环与运营完善

1. 增加任务失败、积压、数据库、资源、数据一致性、安全和审计覆盖规则。
2. 完成告警确认/恢复、趋势、导出、定期只读核查和告警限频。
3. 配置并演练数据库备份/恢复，必要时再接入限频 QQ 主人通知。
4. 根据实际访问量补齐索引、慢查询观测、日志归档与保留策略。

## 9. 测试与验收清单

### 安全

- HTTP、错误 Host、伪造转发头、绕过代理直连、未登录、过期会话、跨站请求、缺失/错误 CSRF、权限不足均无法读取敏感数据或写入。
- 密码、Cookie、CSRF、数据库配置和堆栈不会出现在网页、JSON、日志、快照或导出中。
- 登录与高风险确认被按账号/IP/会话限流；会话登出、禁用账号、改密后立即失效；固定 `admin` 账号不可删除、禁用、降级或改名。
- 验证域名证书自动续期、HSTS、安全 Cookie、可信代理地址校验、Node/MySQL/Redis 端口不在公网监听，以及证书过期告警。

### 查询与性能

- 玩家、操作、事件和告警均可按设计字段组合筛选；空结果、非法分页、过大时间范围和恶意关键词都有稳定响应。
- 大表使用游标和索引，日志页不会执行无界 `OFFSET` 或全表 JSON 扫描。
- 世界总览与玩家详情在数据库短暂不可用时给出受控降级和明确健康状态，不返回伪造数据。

### 数据与回退

- 每个接入领域都覆盖：成功、业务拒绝、异常、重复提交、并发提交、事务失败、重启后重试。
- 审计记录与业务改动同事务提交；业务回滚时不出现伪 committed 记录。
- 单人补偿、状态修复和模板调整可在无后续冲突时回退；发生冲突、战斗、交易、消费或全局联动时必须拒绝。
- 管理员操作、回档操作和告警确认均能从操作编号追到操作者、原因、目标和前后差异。

### 监控

- 模拟数据库失败、任务异常、任务超时、积压旅行、审计写入失败、磁盘余量不足和登录失败突增，验证告警会创建、去重、升级、确认和恢复。
- 监控故障不阻塞玩家核心命令；但审计总账不可写时，相关高风险后台写操作必须 fail closed。
- 验证 `npx tsc --noEmit`，并按当前项目基线区分已有错误与本方案新增错误；同时执行新增测试和 `git diff --check`。

## 10. 明确不做的内容

- 不绕过 HTTPS 反向代理直接暴露 Node、MySQL、Redis 或管理探针；不允许通过“关闭校验”把后台降级为 HTTP。
- 不提供任意 SQL 控制台、任意表/JSON 编辑器或一键全库“回到某一时刻”。
- 不用前端权限隐藏代替服务端鉴权，也不以网页端校验代替业务 service 校验。
- 不让监控自动删除数据、自动封禁玩家或静默修改世界状态。
- 不伪造操作总账启用前的历史；旧数据只作为旧来源联查。
- 不以操作快照取代经验证的 MySQL 备份与恢复演练。

- 世界生态和活动状态查看；经验、掉落、铜币倍率的受控修改，并将网页修改与核查写入 `operation_journals`。
- 定时任务心跳、重复任务失败、滞留旅行、数据库慢响应的监控记录与后台展示。

仍未把以下设计目标标记为完成：每一种玩家有状态操作的事务内总账与领域快照、可冲突检测的回档执行器、TOTP/改密与密码重置、全量世界编辑器、告警确认/恢复、备份验证和生产反向代理配置。这些能力不能以当前第一阶段页面替代。

## 12. 上线前仍需确认的产品边界

本方案现已采用“公网 HTTPS、固定 `admin` owner + 可管理的 admin/viewer 账号、严重告警先在网页显示”的模式。开始实现前需落实：

1. 管理域名、DNS、反向代理（推荐 Caddy/Nginx）、证书、服务器防火墙规则，以及 Node/MySQL/Redis 的仅本机监听策略。
2. 固定主人账号 `admin` 的初始密码哈希；owner 上线后的 TOTP 注册与恢复码保管方式。
3. 需要创建的普通管理员账号、其可授予的角色，以及严重告警是否推送至指定 QQ 主人账号和静默时段。
4. 哪些玩家编辑能力应进入首期白名单；建议先从已有核查、补偿和世界管理动作开始，不开放自由改属性。
5. 生产数据库的备份位置、保留天数与允许的停机/恢复窗口。

确认后，继续按阶段 A -> B 的顺序实施：先补齐可追溯的领域操作与快照，再逐步开放可控修改与回退能力。
