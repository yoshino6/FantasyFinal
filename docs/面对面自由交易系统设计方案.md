# 面对面自由交易系统设计方案

## 1. 目标与定位

在既有「万叶联市」之外，新增一个**两名玩家同坐标、双方自主出价、双方最终确认后即时结算**的面对面交易系统。

它解决的是临时换材料、队友互补、当面赠送和熟人间以物易物；不替代公开市场的价格发现与大额匿名流通。

| 系统 | 核心场景 | 对手方 | 价格 | 主要限制 |
| --- | --- | --- | --- | --- |
| 万叶联市 | 大宗买卖、找价格、面向全服 | 匿名订单簿 | 公开参考价与挂单区间 | 手续费、订单有效期、周成交额 |
| 面对面自由交易 | 同行互换、临时补给、熟人赠送 | 指定且同坐标的玩家 | 双方自由议定 | 当面、双确认、托管、净流入额度与风控 |

### 1.1 v1 必须遵守的决定

- 两人必须在**相同区域、相同 `x/y/z` 坐标**才能发起、接受和最终结算；不能远程指定交易。
- 交易中的物品和铜币一旦放入报价，即进入系统托管；取消、超时、失败都会原样退回，不能出现“先给一方、再等另一方”的半完成交易。
- 任意一方修改物品、数量或铜币，都会使双方的锁定与最终确认失效；旧按钮也只能作用于当前版本，不能被截屏/旧消息“偷换报价”。
- v1 只开放与万叶联市同一批**可交易堆叠物**：材料、药剂、食物及普通消耗品。装备实例、图纸、货币物品、任务/剧情物、礼物、家具、地图与特殊物一律不开放。
- 铜币可作为双方报价的一部分；银币、金币等物品形态的货币不开放直接转移，避免绕过货币账本。
- 不要求好友关系，因此可以帮助陌生队友；但大额单向赠送会受到更严格的净流入额度约束。
- v1 不因交易次数、金额或“首次交易”自动发材料、货币或好感，避免小号刷互动奖励。

## 2. 当前项目基础与落点

现有代码已经具备本方案所需的大部分基础，不应重新造一套背包或坐标系统。

| 已有能力 | 当前位置 | 本系统的使用方式 |
| --- | --- | --- |
| 同坐标玩家校验 | `src/game/dungeon.service.ts` 的 `interactDungeonPlayer` | 抽取为可复用的“双方同坐标且非本人”校验；交易全流程复验 |
| 坐标互动中的 `[交易]` 入口 | `src/response/adventure.ts` | 补齐单个玩家互动面板的入口，并接入正式路由/处理器 |
| 市场托管与事务结算 | `src/game/market.service.ts` | 沿用 `withTransaction`、库存行锁、铜币预扣、`INSERT ... ON DUPLICATE KEY UPDATE` 的结算方式，不复用市场订单表 |
| 可交易物品字段 | `item_definitions.is_tradeable`、`stackable`、`trade_price`、`item_category` | 复用市场 v1 的物品白名单，而不是仅凭 `is_tradeable=1` 放开全部物品 |
| 好友与星誓关系 | `player_relationships`、`player_oaths` | 用 `became_friends_at`、好感与星誓状态决定较高的净赠与额度 |
| 社交事件与群内主动消息 | `player_events`、`MessageDirect`、群频道记录 | 写入双方交易事件；在同一群会话中 @ 被邀请者并附接受/拒绝按钮，无法主动送达时回退至 `/交易` 待办 |

现有坐标互动的多目标面板已经输出 `/玩家交易 <游戏ID>`，但 `src/index.ts` 尚未注册这个命令，单一玩家的“玩家互动”面板也尚未显示交易按钮。它们应作为本功能的首批接入点。

## 3. 玩家体验与按钮设计

### 3.1 入口

当玩家使用 `/坐标互动 玩家 <ID>`，或在同格多目标互动面板选择玩家时，显示：

```text
# 玩家互动

ID：1024
昵称：洛恩

[交易] [邀请入队] [加好友/赠礼]
```

- `[交易]` 发送 `/玩家交易 1024`。没有手输对方名字、QQ 号或交易编号的步骤。
- 只有服务器重新确认目标仍在同一格后，才创建交易邀请；玩家刚走开、进战斗或处于不可行动状态时直接说明原因。
- 单个玩家互动面板与多目标互动面板使用同一入口，避免一处能交易、另一处没有按钮。

### 3.2 从邀请到成交

```text
同格互动
  → 发起 `/玩家交易 <目标ID>`
  → 对方接受（90 秒内）
  → 双方各自编辑报价（5 分钟会话）
  → 双方锁定报价
  → 双方最终确认同一版本
  → 单事务交割，双方收到成交回执
```

发起者看到：

```text
# 交易邀请已发出

向【洛恩】发起面对面交易。
请等待对方在 90 秒内接受；双方离开此处或进入战斗，邀请会自动失效。

[查看交易] [取消邀请]
```

若发起命令来自群聊，应在该群内主动 @ 对方并发出：

```text
# 面对面交易邀请

【伊芙】希望与你交易。请确认你们仍站在同一位置。

[接受交易] [拒绝]
```

若平台不支持向目标私聊主动送达，或发起于私聊，则不应假定一定能推送成功；目标玩家随时通过 `/交易` 看到待处理邀请并接受。这是可靠的降级路径，不影响交易正确性。

### 3.3 交易面板

每一位参与者都通过自己的 `/交易` 或 `[查看交易]` 打开同一笔会话的个人面板。面板必须同时展示双方**实际已托管**的报价，而不是只展示输入草稿。

```text
# 面对面交易 · 与洛恩

你给出
微光草药 × 12
铜币 × 300

对方给出
哥布林耳 × 8
铜币 × 0

状态：报价编辑中 · 版本 4 · 4 分 18 秒后自动退回
提示：任一方修改报价，双方确认都会失效。

[添加物品] [设置铜币] [取回我的报价]
[锁定我的报价] [取消交易]
```

物品选择页采用已验证的背包分页/搜索模式：

```text
# 选择交易物品

【怪材】哥布林耳 × 36      [+1] [输入数量]
【药剂】微光草药 × 18      [+1] [输入数量]

[材料] [消耗品] [搜索] [上一页] [下一页] [返回交易]
```

- `+1` 可以直接执行；`输入数量` 只预填 `/交易放入 <物品编号> `，让玩家补数量后再发送，避免误把整组材料放入。
- 铜币使用 `/交易铜币 <数量>` 设定为自己的总报价金额，而不是“追加金额”；面板始终显示最终数字。
- 物品操作仅针对当前用户唯一的活跃会话。交易编号仅由按钮和服务端状态携带，玩家不需要记忆或输入它。
- 分页、类别、搜索与返回按钮使用 `Format` 的 Markdown/Button 组合；无参数跳转可 `autoEnter: true`，需要输入数量/关键词的按钮仅预填命令，不自动提交。

### 3.4 锁定与最终确认

为防止临时改价、手滑和旧消息重放，采用两道明确但不冗长的确认。

1. 玩家点击 `[锁定我的报价]` 后，自己的报价不可编辑。
2. 双方都锁定后，面板进入“请核对最终报价”，显示逐项物品、数量、铜币与剩余时间。
3. 两人分别点击蓝色 `[最终确认交易]`；第二人确认时由服务端在一个数据库事务内交割。
4. 任何一方点击 `[解锁并修改]`、添加/取回物品、修改铜币，均递增报价版本并清除**双方**的锁定与最终确认。

最终确认页示例：

```text
# 请最终确认

你将获得：哥布林耳 × 8
你将交付：微光草药 × 12、铜币 × 300

对方已确认：是
本次价值差：正常范围

[最终确认交易] [解锁并修改] [取消交易]
```

成交后双方各收到自己的回执；群内只显示“【A】与【B】完成了一笔面对面交易”，不公开物品、数量、铜币和价值，保护协商隐私。

## 4. 资格、物品与数值建议

以下数值是**保守的 v1 建议值**，用于上线前评审；应在灰度期根据真实产出、市场参考价和风险命中率调整，不应直接改动现有市场额度。

### 4.1 交易资格

双方都必须同时满足：

- 已注册冒险者，等级不低于 Lv.15。
- 角色创建满 14 天。
- 不处于战斗、移动、采集、家园室内、账号注销流程或其他未结束的面对面交易中。
- 未被管理员冻结直接交易资格，且没有需要人工处理的高风险冻结。
- 与对方处在同一区域、同一 `x/y/z` 坐标，且不是自己。

市场目前的门槛是 Lv.10、登记冒险者、注册满 72 小时。直接交易可以指定对象且允许不等价赠送，因此应比市场严格，而不是复制原门槛。

### 4.2 v1 可交易范围

与万叶联市的 v1 白名单保持一致：

```text
is_tradeable = 1
AND stackable = 1
AND trade_price > 0
AND item_type IN ('material', 'consumable')
AND item_category NOT IN ('特殊', '地图', '货币', '任务', '剧情', '图纸', '礼物', '家具')
```

这样可避免现有 `player_item_instances` 中的品质、耐久、锻造词条和装备状态被当作普通数量物品扣除。也避免把任务、主线、地图和礼物系统的专属物品变成转移渠道。

第二期若开放装备，必须按**实例 ID**托管和转移，并在确认页展示品质、耐久、熔铸、词条、绑定状态和来源摘要；不能将装备直接塞进 `player_inventory` 数量表。第二期不属于本方案的 v1 实施范围。

### 4.3 估值与额度

面对面交易不设公开价格区间，但风险系统需要统一尺度。每项堆叠物的内部估值 `V` 为：

```text
若存在有效市场参考价：V = 市场参考价
否则：V = max(1, NPC 回收价 × 2)

一方报价估值 = 铜币 + Σ(物品数量 × V)
净流入估值 = 收到报价估值 - 给出报价估值
```

- 估值只用于额度、异常检测和管理审核，不向玩家强制规定成交价格。
- 没有成交量的物品沿用市场已使用的 `trade_price × 2` 初始化逻辑，保证新材料也有一致、可解释的保守估值。
- 市场价格被风控暂停、物品未在 v1 白名单或估值无效时，直接不能放入面对面交易，不给绕过市场风控的入口。

建议限额如下：

| 指标 | 新交易者（满足资格后前 14 天） | 普通交易者 | 可信关系* |
| --- | ---: | ---: | ---: |
| 单笔单方报价估值上限 | 20,000 | 80,000 | 120,000 |
| 每日双方报价总额上限 | 40,000 | 160,000 | 240,000 |
| 同一对角色 7 日双方报价总额 | 60,000 | 160,000 | 240,000 |
| 每日净流入上限 | 4,000 | 12,000 | 30,000 |
| 7 日净流入上限 | 12,000 | 36,000 | 90,000 |
| 每日完成笔数 | 3 | 8 | 10 |

\*可信关系：好友已满 14 天且好感达到 120，或处于有效星誓关系。可信关系只是提高上限，**不会**免除同坐标、托管、双确认和审计。

这些额度使普通等价互换更顺畅，也允许小额赠与；但一个新小号无法在一天内把高价值资源或大量铜币集中输送给主号。大宗、跨时段买卖仍应使用万叶联市。

### 4.4 无偿赠送与互动边界

- 某一方报价为零是合法的，并在面板上明确标为“无偿赠与”。
- 无偿赠与、极不等价互换首先消耗接收方的净流入额度；额度不足时应直接拒绝并提示“请改为更等价的交换、等待额度刷新或使用万叶联市”。
- 不对好友、队友或星誓关系设置无上限白名单；关系本身可以由小号养成，不能成为风控豁免。
- 不给完成交易自动发奖励。后续如果要做“商旅委托”或交易纪念，应以不同玩家、不同区域、风险正常、无单向赠与为前置，并先观察至少两个版本周期的数据。

## 5. 状态机与异常处理

### 5.1 状态机

```text
requested --接受--> negotiating --双方锁定--> confirming --双方最终确认--> settled
     |                    |                    |                         
     └--拒绝/超时-------> declined/expired     └--取消/超时/离开-------> cancelled/expired

任意报价修改：negotiating 或 confirming → negotiating（报价版本 +1，双方锁定/确认清空）
风控或管理员冻结：requested/negotiating/confirming → blocked（不允许继续结算，按审核动作退回或处理）
```

| 场景 | 系统行为 |
| --- | --- |
| 邀请 90 秒未接受 | 标记 `expired`，无资产需要退还 |
| 协商 5 分钟无操作 | 标记 `expired`，事务内退还全部托管物和铜币 |
| 任一方离开同格、开始移动或进入战斗 | 立即取消并原样返还托管；未开始结算时绝不扣留资产 |
| 任一方主动取消 | 事务内将双方托管全部返还，另一方收到取消通知 |
| 旧按钮、已取消会话或错误参与者操作 | 不修改任何资产，提示“交易已更新或已结束，请重新打开 `/交易`” |
| 第二次最终确认与第一次并发到达 | 仅第一个成功将状态从 `confirming` 改为 `settled`；其余请求读取到已结算状态，不会重复发放 |
| 交割时发现库存/坐标/资格变化 | 整笔事务回滚；若会话已不满足面对面条件则取消并返还 |
| 服务重启或定时任务漏跑 | 每次读取/写入交易都顺带清理到期会话；另有定时清理作为补偿，不依赖单一 cron |

### 5.2 同坐标与行动互斥

交易服务应提供统一的 `assertTradeFaceToFace`，在创建邀请、接受邀请、锁定、最终确认和结算时都重新查询并校验：

```text
current_region_id 相同
pos_x 相同
pos_y 相同
pos_z 相同
双方均不是 NPC、均为 active，且没有战斗/移动/采集等冲突状态
```

移动、进入战斗、采集、进出家园、账号注销等入口需要先检查是否有活动交易：存在时调用同一个“取消并返还”服务，再继续原操作或提示玩家。不能只在交易按钮处做一次位置判断，否则玩家可以在报价后离开并造成悬挂资产。

## 6. 托管、并发与交割设计

### 6.1 放入、取回与锁定

每次放入或取回物品、设置铜币，都在一个 `withTransaction` 内完成：

```text
锁定交易会话
→ 锁定双方角色（固定按 character_id 升序）
→ 校验参与身份、状态、期限、同坐标、资格、额度
→ 锁定所涉及 player_inventory 行（item_id 升序）
→ 从背包扣除/向背包返还，或预扣/返还铜币
→ 写入/更新托管报价
→ 报价版本 +1，清空双方锁定与最终确认
→ 写入操作事件
```

铜币不是“最终确认时再检查余额”，而是在设置报价时预扣到交易托管余额。这样其他命令无法把同一批铜币或物品重复消费。

### 6.2 最终结算

```text
锁定交易会话与双方角色（固定顺序）
→ 校验状态为 confirming、双方确认版本 = 当前报价版本、未过期且仍同格
→ 锁定全部托管物行与额度统计行
→ 再计算双方估值、净流入、单笔/日/周/同对上限与风险结果
→ 将 A 的托管物和铜币发给 B，将 B 的托管物和铜币发给 A
→ 写入不可变成交记录、双方 player_events、额度统计与风险记录
→ 标记 settled，删除活动参与锁
→ 提交
```

交割中若任何一步失败，数据库回滚到提交前状态：托管仍在、报价仍在，双方不会各拿到一半。若失败原因是过期或不再同格，改走“取消并返还”事务。

### 6.3 防死锁与幂等

- 所有涉及双方的流程先按 `character_id` 升序锁定角色，再按 `item_id` 升序锁定库存/托管行。
- 每个角色同一时刻只能拥有一笔 `requested`、`negotiating` 或 `confirming` 会话；用数据库主键保证，而不是只靠“先查后写”。
- 每个外部按钮请求带平台事件唯一键或服务端操作 UUID，成交表对 `session_id` 保持唯一，防重复投递。
- 到期清理、取消、风控冻结和双方确认都以会话状态 `FOR UPDATE` 判定是否仍可变更；返还只执行一次。

## 7. 数据库设计

表名使用 `player_trade_*`，避免与匿名市场的 `market_*` 混淆。以下为结构级设计，字段类型可与现有 MySQL 风格保持一致。

### 7.1 会话与活动参与锁

```text
player_trade_sessions
- id BIGINT PK
- initiator_character_id
- target_character_id
- state ENUM('requested','negotiating','confirming','settled','declined','cancelled','expired','blocked')
- region_id, pos_x, pos_y, pos_z              -- 发起位置快照，审计用途
- quote_revision INT UNSIGNED DEFAULT 1
- initiator_locked_revision INT NULL
- target_locked_revision INT NULL
- initiator_confirmed_revision INT NULL
- target_confirmed_revision INT NULL
- request_expires_at, expires_at, settled_at, cancelled_at
- source_scope, source_channel_id, source_bot_id -- 仅用于通知回送，可为空
- cancel_reason VARCHAR(48) NULL
- created_at, updated_at

索引：
  (initiator_character_id, state, updated_at)
  (target_character_id, state, updated_at)
  (state, expires_at)
```

```text
player_trade_active_participants
- character_id PK
- session_id UNIQUE
- expires_at

用途：每个活跃参与者仅一行。创建邀请时插入双方记录，完成/取消/超时后删除；
主键从数据库层阻止一个角色同时开启多笔交易。
```

### 7.2 报价与托管

```text
player_trade_offers
- session_id
- character_id
- copper_escrow BIGINT UNSIGNED DEFAULT 0
```

### 7.4 账号注销与历史保留

- 注销前必须先取消该角色的活动交易并返还托管；不能靠外键级联删除托管资产。
- `player_trade_sessions` 的未结算记录可随角色清理，但 `player_trade_settlements` 作为跨玩家历史保留，参与者外键应允许 `ON DELETE SET NULL`，同时保留角色名快照和报价快照。
- 账号恢复快照中不恢复已结束的跨玩家交易，也不恢复活动交易；避免恢复一个已被对方结算/取消的旧会话。
- 现有账号删除服务的跨玩家/短时状态排除表清单需要加入这些交易表，并加入“先取消再删除”的显式步骤。

## 8. 风控策略

### 8.1 第一层：产品规则

- 同格、双人、双锁定、双最终确认、短时过期与托管，阻断远程批量搬运和单方面骗取。
- 角色资格与活跃会话唯一锁，限制批量新号同时向同一主号供货。
- v1 只允许市场白名单的堆叠物，任务物、装备实例和特殊奖励不能转移。
- 单笔、日、周、同对角色和净流入额度共同约束；只限制单笔金额不足以处理拆单。

### 8.2 第二层：关系与资金流分析

每次最终确认前计算下列信号，达到阈值可拒绝、延迟或写入人工审核队列：

| 风险信号 | 建议处理 |
| --- | --- |
| 新交易者连续向同一老角色单向转入，且接近净流入上限 | 拒绝超过额度部分，写入风险记录 |
| 同一对角色短时间多次拆单，累计接近同对周上限 | 合并计算后限制，并标记“拆单规避” |
| 多个低等级/新角色向同一角色集中输送同类高价值物 | 提升接收者风险分，管理员可临时冻结直接交易 |
| 报价长期极端不等价且无可信关系 | 保留交易但收紧净流入额度；连续命中时进入人工审核 |
| 被市场风控冻结的角色尝试直接交易 | 直接拒绝，避免在两个系统间绕行 |
| 同一批角色仅互相交易、几乎无正常产出/玩法事件 | 标记观察，不自动没收资产 |

不要以 IP、设备指纹或“疑似同设备”作为唯一封禁依据：平台权限、网络环境与家庭共用设备都会产生误伤。它们若在合规前提下可用，也只应成为管理员复核的辅助证据。

### 8.3 处置原则

- **额度不足**：当场拒绝，不扣任何托管资产。
- **中风险**：可以完成，但记录 `flagged`；灰度期先观测命中率。
- **高风险**：不允许新建会话，管理员冻结前先事务取消并返还所有未结算会话。
- **人工修正**：不篡改历史成交行；以独立的补偿/回退操作记录原因、操作者、关联成交 ID 和前后快照。
- **管理员工具**：需要有按角色、对手、日期、物品、风险状态筛选的成交视图，以及“冻结直接交易”“取消并返还活动会话”“标记已复核”三类最小操作。

当前背包是按物品总数量堆叠，并不保存每一单位堆叠物的连续来源链。因此 v1 可以准确记录“这次交易交付了什么”，但不能在物品与其他同类物品混合后精确追踪每一件的后续去向。若未来需要逐件追溯，必须单独设计 `inventory_lots`/来源批次系统，不能在自由交易上线后假装已有该能力。

## 10. 实施顺序

1. 确认 v1 白名单、资格门槛与上表额度；先不开放装备实例。
2. 增加数据表、活动参与唯一锁、结算历史与安全索引；以 `game_data_migrations` 记录一次性迁移。
3. 实现纯服务层：资格、同坐标、报价托管、取消/过期返还、双确认交割。
4. 为服务层写双角色集成测试，再接入路由和按钮面板。
5. 接入账号注销、移动/战斗冲突取消、管理员冻结与审计查询。
6. 小范围灰度两周：先记录中风险标记、每日检查净流入和同对角色集中度，再决定高风险自动限制阈值。
7. 灰度稳定后再评估装备实例交易、交易纪念和更高可信关系额度；每项都单独出方案。

## 11. 验收标准与测试矩阵

### 11.1 玩家流程

- 同一格的两名符合资格玩家可从单目标和多目标互动面板发起交易。
- 不同区域、不同楼层、相邻但不同格、自己对自己、家园内、战斗/移动/采集中均不能发起或接受。
- 双方能各自加入多种可交易堆叠物和铜币；面板即时显示双方当前托管报价。
- 一方改价后，双方锁定和确认都被清除；旧版本确认按钮不能成交。
- 双方最终确认同一版本后，物品和铜币一次性交换，双方回执与成交历史一致。
- 任何一方取消、拒绝、超时、离开同格或进入冲突状态后，所有托管资产原样返还一次且仅一次。

### 11.2 安全与并发

- 同一库存物品不能同时放入市场订单和面对面交易，也不能在两个面对面会话中重复托管。
- 同一角色并发点两次邀请，数据库只允许一笔活动会话。
- 两人同时点最终确认、多次重复投递同一确认、定时清理与取消并发时，最多产生一条 `settled` 记录、一次资产发放。
- 会话过期后点击任意旧按钮不会改变余额、库存或成交记录。
- 无权限的第三人即使猜到会话编号，也无法读取报价、确认、取消或取回。

### 11.3 风控与数据生命周期

- 新交易者、普通交易者、可信关系分别正确应用单笔、日、周、同对和净流入限制。
- 单向赠送、拆单、多人汇入、市场冻结绕行都生成预期的拒绝或风险记录。
- 管理员冻结时活动会话全部返还；历史成交保留且可按双方筛选。
- 注销账户前活动会话被安全取消，已结算历史仍能为对手方审计；恢复账户不复活旧会话。

## 12. 上线后的观察指标与后续建议

首两周每天观察以下指标：

- 面对面交易完成数、取消率、超时率、每笔报价版本次数。
- 新交易者的净流入分布、同对角色集中度、前十接收者的来源角色数。
- 与万叶联市相同物品的成交量和参考价是否出现异常迁移。
- 风险标记总量、人工复核后的误报率与真实违规命中率。

合理化建议：

- **先把面对面交易做成低摩擦的社交交换，而非零限制的私下市场。** 同坐标、短会话与按钮化报价已经足够方便；大额流通交由匿名市场，经济更稳定。
- **先开放堆叠物，后开放装备实例。** 装备的品质、耐久和词条使“看起来能交易”与“能安全、可审计地交易”是两件事，分期可避免一次性扩大风险面。
- **额度应以净流入和同对累计为核心。** 仅限制单笔会被拆单绕过；仅限制总成交额又会误伤正常等价互换。
- **关系只提升额度，不成为免检凭证。** 这既鼓励玩家建立真实社交，也避免创建几个互加好友的小号就绕过系统。
- **不要给交易直接产出奖励。** 如果未来想增强氛围，可先加入无数值的“交易记录/相遇记忆”；任何可刷资源的交易成就都应在有足够风控数据后再讨论。

本文件只定义方案和建议值，未修改交易、背包、数据库或市场数值；需确认第 4.1 与第 4.3 的资格/额度后再进入实现。
