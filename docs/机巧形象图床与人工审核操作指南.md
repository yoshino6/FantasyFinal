# 机巧形象：图床与人工审核操作指南

更新日期：2026-09-07。存储方案：Cloudflare R2 + Worker；审核方式为**游戏管理后台人工审核**，不需要 AI 接口或商业图片审核服务。

## 1. 改用 Cloudflare R2，怎么接入

本指南改为推荐 **Cloudflare R2 + 一个上传 Worker**。R2 保存审核通过的图片；Worker 是部署在 Cloudflare 上的小型上传接口，负责验证游戏服务器的密钥并写入 R2。人工审核仍在游戏管理后台进行。

**当前代码实际支持 `imgbb` 和 `generic`，没有原生 `r2` 配置项。** 本指南用 Worker 对接现有 `generic` 协议，部署好 Worker 后即可按本文填写配置。不要填写 `provider: r2`，也不能把 R2 的 S3 Endpoint 直接当作 `uploadUrl`。

本次仅更新操作指南，附可复制的 Worker 示例；没有替你开通付费服务、创建桶、部署 Worker 或修改游戏密钥。本文 Worker 不需要单独创建 S3 Access Key，使用 R2 绑定访问存储。[Workers 访问 R2](https://developers.cloudflare.com/r2/api/workers/workers-api-usage/)

| 你需要准备 | 用途 |
| --- | --- |
| Cloudflare 账号并开通 R2 | 管理图片存储 |
| 一个专用 R2 桶 | 只存审核通过的机巧形象 |
| 一个 Worker | 接收游戏后台上传，校验上传令牌 |
| 自己生成的上传令牌 | 只交给 Worker 和游戏服务器 |
| 图片公开访问地址 | QQ 用它读取图片；测试用 r2.dev，正式建议自定义域名 |

### 费用先了解

R2 **Standard 标准存储**当前每月免费额度为 10 GB-month 存储、100 万次 A 类操作、1,000 万次 B 类操作；R2 本身不收互联网出站流量费。超额标准价格为存储 $0.015/GB-month、A 类 $4.50/百万次、B 类 $0.36/百万次，官方按计费单位向上取整。免费额度不适用于低频存储，所以这里选择 Standard。按 2026-09-07 官方价目记录，后续以账单为准。[R2 官方价格](https://developers.cloudflare.com/r2/pricing/)

Worker 有独立的额度和计费规则；本方案只有上传经过 Worker，图片读取直接走桶公开域名。域名购买也可能产生额外费用，不能把“出站流量免费”理解成所有使用都免费。[Workers 官方价格](https://developers.cloudflare.com/workers/platform/pricing/)

容量估算：假设平均每张压缩图 200 KB，10,000 张约占 2 GB；实际应看控制台用量，旧图未清理也会继续占空间。这是估算，不是每张图片的固定大小。

## 2. 流程与三个地址

```text
玩家发图 → 本机校验与压缩 → 本机待审队列
  → 游戏管理后台人工审核
      ├─ 驳回：清理待审文件，保留原形象
      └─ 通过：游戏服务器 → 带密钥的 Worker /upload → R2 桶
          → 返回公开图片直链 → 写入游戏形象
          └─ 上传失败：保持待审核，保留原形象

QQ 打开详情 → 通过 R2 公开域名读取审核通过的图片
```

| 地址 | 示例 | 填在哪里 |
| --- | --- | --- |
| Worker 上传地址 | `https://ff-portrait-upload.你的子域.workers.dev/upload` | 游戏 `host.uploadUrl` |
| 图片公开根地址 | `https://pub-你的编号.r2.dev` 或 `https://img.你的域名` | Worker `PUBLIC_BASE_URL` |
| R2 S3 API 地址 | `https://账号编号.r2.cloudflarestorage.com` | 本方案不用；它不是图片公开地址 |

不要把上传密钥放进图片 URL。待审图片继续仅存本机，公开桶只放审核通过的图片。R2 本身和本文 Worker 都不做内容审核，不能代替管理员判断。

## 3. 按顺序配置 Cloudflare

### 第一步：开通 R2 并建桶

1. 登录 [Cloudflare 控制台](https://dash.cloudflare.com/)。
2. 找到 **Storage & databases → R2 → Overview**（界面也可能显示 R2 Object Storage）。首次使用按页面完成 R2 订阅开通；若要求付款资料，在确认费用后填写。
3. 创建桶，建议名称 `fantasyfinal-portraits`；这个名字后面绑定 Worker 时会用到。
4. 选择 **Standard** 标准存储。不要给这个桶配置自动删除所有对象的生命周期规则，以免正在使用的人偶图片过期消失。
5. 桶专门存公开形象，不放数据库备份、密钥或待审图片。

入口及订阅流程依据 [R2 入门文档](https://developers.cloudflare.com/r2/get-started/)。具体按钮名称以当前控制台为准。

### 第二步：获得图片公开地址

你现在没有域名，可以先做小范围测试：进入桶 **Settings → Public Development URL**，启用并复制系统分配的 `https://pub-……r2.dev` 地址，记为 `PUBLIC_BASE_URL`。

**r2.dev 只用于开发测试，有速率限制，不作为正式服长期地址。** 正式使用时，准备一个加入同一 Cloudflare 账号的域名，在桶 **Settings → Custom Domains → Add** 里绑定例如 `img.example.com`，等待状态为 Active；之后把 `PUBLIC_BASE_URL` 改为 `https://img.example.com`。通过桶的自定义域名功能绑定，不要自行把域名 CNAME 到 r2.dev。[公开桶与自定义域名](https://developers.cloudflare.com/r2/buckets/public-buckets/)、[开发地址限制](https://developers.cloudflare.com/r2/platform/limits/)

此时可以在桶控制台手动上传一张自己有权使用的合规测试图，检查“公开根地址/对象名”能否在未登录浏览器直接显示。测试结束可以删除这张测试图。日常玩家图片必须走游戏人工审核流程。

**国内网络与手机 QQ 的可达性仍需实测，换成 R2 不代表能保证访问速度。** 已经写进游戏的 r2.dev 旧链接不会随变量修改自动变成新域名；正式放开玩家上传前先确定正式域名。

### 第三步：创建上传 Worker

1. 在 Cloudflare **Workers & Pages** 新建一个 Worker，可以从 Hello World 示例开始；建议名称 `ff-portrait-upload`。
2. 打开该 Worker 的代码编辑页面，用下文“上传 Worker 完整代码”替换示例代码。
3. 在 Worker 的 **Bindings → Add binding → R2 bucket** 添加绑定：变量名必须为 `PORTRAITS`，选择刚创建的 `fantasyfinal-portraits` 桶。
4. 在 Worker **Settings → Variables and Secrets** 添加文本变量 `PUBLIC_BASE_URL`，值为第二步得到的公开根地址，不加文件名。
5. 再添加 **Secret 类型**的 `UPLOAD_TOKEN`。值使用密码管理器生成的至少 32 字符随机密钥，建议 64 位随机十六进制；不要使用登录密码或本文示例文字。
6. 保存配置并部署新版本。复制实际 Worker 地址，在末尾加 `/upload`，作为游戏上传地址。

创建与部署参考 [Workers 控制台入门](https://developers.cloudflare.com/workers/get-started/dashboard/)，Secret 配置参考 [官方 Secret 说明](https://developers.cloudflare.com/workers/configuration/secrets/)。

Worker 通过 `PORTRAITS` 绑定操作指定桶；`UPLOAD_TOKEN` 是本系统自定义的服务端上传口令，**不是 Cloudflare 账号 API Token，也不是 R2 S3 密钥**。只有持有该口令的游戏服务器能上传，公开读图无需口令。

### 上传 Worker 完整代码

下面是独立的 JavaScript Worker 示例，复制到 Cloudflare Worker 编辑器，**不要粘贴到游戏配置 YAML**。文件名与 WebP 格式限制对应当前游戏压缩输出；请求体上限 3 MiB，图片上限 2 MiB。

```javascript
const reply = (status, body) => Response.json(body, {
  status,
  headers: { 'Cache-Control': 'no-store' }
});

export default {
  async fetch(request, env) {
    const path = new URL(request.url).pathname;
    if (path !== '/upload') return reply(404, { message: 'Not found' });
    if (request.method !== 'POST') return reply(405, { message: 'POST required' });
    if (!env.UPLOAD_TOKEN || env.UPLOAD_TOKEN.length < 32 || !env.PORTRAITS) {
      return reply(503, { message: 'Worker configuration incomplete' });
    }
    if (request.headers.get('Authorization') !== `Bearer ${env.UPLOAD_TOKEN}`) {
      return reply(401, { message: 'Unauthorized' });
    }

    let base;
    try {
      base = new URL(env.PUBLIC_BASE_URL);
      if (base.protocol !== 'https:' || base.username || base.password ||
          base.search || base.hash || base.pathname !== '/') throw new Error();
    } catch {
      return reply(503, { message: 'Invalid PUBLIC_BASE_URL' });
    }
    const contentType = request.headers.get('Content-Type') || '';
    if (!contentType.toLowerCase().startsWith('multipart/form-data;')) {
      return reply(415, { message: 'multipart/form-data required' });
    }

    const maxBody = 3 * 1024 * 1024;
    if (!request.body || Number(request.headers.get('Content-Length')) > maxBody) {
      return reply(413, { message: 'Request too large or empty' });
    }
    let form;
    try {
      // 不依赖可伪造或缺失的 Content-Length，逐块限制实际请求体大小。
      const reader = request.body.getReader();
      const chunks = [];
      let size = 0;
      while (true) {
        const { done, value } = await reader.read();
        if (done) break;
        size += value.byteLength;
        if (size > maxBody) {
          await reader.cancel();
          return reply(413, { message: 'Request too large' });
        }
        chunks.push(value);
      }
      const body = new Uint8Array(size);
      let offset = 0;
      for (const chunk of chunks) { body.set(chunk, offset); offset += chunk.byteLength; }
      form = await new Response(body, { headers: { 'Content-Type': contentType } }).formData();
    } catch {
      return reply(400, { message: 'Invalid upload body' });
    }
    const entries = [...form.entries()];
    const file = form.get('file');
    if (entries.length !== 1 || entries[0][0] !== 'file' ||
        !file || typeof file === 'string' || file.type !== 'image/webp' ||
        !/^[a-f0-9]{32}\.webp$/.test(file.name) || file.size < 12 ||
        file.size > 2 * 1024 * 1024) {
      return reply(400, { message: 'One normalized WebP image required' });
    }
    const bytes = new Uint8Array(await file.arrayBuffer());
    const ascii = (start, end) => String.fromCharCode(...bytes.slice(start, end));
    if (ascii(0, 4) !== 'RIFF' || ascii(8, 12) !== 'WEBP') {
      return reply(400, { message: 'Invalid WebP header' });
    }
    const key = `portraits/${file.name}`;
    try {
      await env.PORTRAITS.put(key, bytes, {
        httpMetadata: { contentType: 'image/webp', cacheControl: 'public, max-age=86400' }
      });
      return reply(200, { url: new URL(key, base).href });
    } catch {
      return reply(502, { message: 'R2 upload failed' });
    }
  }
};
```

这段代码不提供匿名上传、文件列表或删除接口。格式校验不是内容审核：它信任持有上传密钥的游戏服务器已经完成人工审批，勿把密钥提供给玩家。桶、Worker、公开域名均应由你掌控。

## 4. 填写游戏配置

在项目根目录 `alemon.config.yaml` 的**已有** `FantasyFinal:` 节点下合并以下配置。`token` 与 Worker 的 `UPLOAD_TOKEN` 完全相同，不带 `Bearer ` 前缀。

```yaml
FantasyFinal:
  automatonPortrait:
    host:
      provider: generic
      uploadUrl: "https://ff-portrait-upload.你的子域.workers.dev/upload"
      token: "替换成Worker里同一份UPLOAD_TOKEN"
```

这里仍然写 `generic`，因为游戏通过 Worker 的通用接口上传。图片地址由 Worker 返回，不在 YAML 中填 `PUBLIC_BASE_URL`。**把旧的 `provider: imgbb` 和 `apiKey` 配置替换掉，不要保留两个 `host` 节点。**

人工审核依赖现有管理后台。若曾关闭，在已有配置里改为：

```yaml
FantasyFinal:
  adminWeb:
    enabled: true
```

两个示例实际要合并到同一个 `FantasyFinal:` 下。缩进用空格；不要覆盖数据库、QQ、管理员密码、端口或公网地址。上传密钥只放在服务器私密配置与 Worker Secret，不提交 Git。

保存后按现有进程管理方式重新加载游戏配置。本次文档修改本身不需要重新构建代码；如果此前人工审核功能的新代码尚未部署，先按现有流程构建部署（项目命令 `npm run build`）再重启，正常启动初始化会建立所需表。不要在正式服运行时另外启动开发实例。

## 5. 打开后台审核

如果游戏运行在你当前电脑，且后台沿用默认本地配置，在浏览器打开：

```text
http://127.0.0.1:17118/admin
```

使用你现有的管理后台账号和密码登录，点击左侧 **机巧形象审核**。

如果游戏运行在远程服务器，电脑上的 `127.0.0.1` 指的是你的电脑，不是服务器。已有 HTTPS 后台地址就继续用已有地址。没有公网后台域名但已经有 SSH 登录方式时，可以建立本地隧道：

```bash
ssh -N -L 17118:127.0.0.1:17118 你的SSH用户名@你的服务器地址
```

隧道保持运行，再在自己电脑打开上面的本地地址。这适用于后台仍采用本地访问配置的情况；已经设置 `publicBaseUrl` 的后台继续使用其 HTTPS 地址。无需为了图床而公开整个游戏后台。

没有后台账号或忘记密码时，应沿用已有的管理员账号管理流程；本功能不提供新的默认密码，也不会替换原密码。

### 审核页面怎么用

1. 默认显示 **待审核**。可按玩家名、QQ 号、机巧名搜索，并用上一页、下一页翻页，每页 20 条。
2. 检查图片，可点击预览在新标签页查看完整图片。
3. 逐项检查是否包含色情、赌博、毒品内容或真人照片。真人局部、拼贴中的真人、加滤镜的真人照片也应拒绝；无法确认时请驳回，要求更换清晰的非真人图片。
4. 填写审核说明。合规时可写“卡通机械人偶，未发现违禁内容及真人照片”。
5. 点击 **通过并发布**，确认后由服务器上传图床并更新游戏形象。
6. 不合规则写具体原因并点击 **驳回**，例如“请使用非真人图片，此图包含真人照片”。驳回原因会显示给玩家。
7. 切换 **已通过 / 已驳回 / 已取消 / 全部**，可查处理人、时间和说明。通过与驳回也会记入审计总账。

人工审核完全依赖管理员判断；系统不会偷偷调用 AI，也不会自动判断黄赌毒或真人内容。无人处理时，图片保持待审核，不会自动通过。

## 6. 玩家怎么上传

1. 输入 `/机巧`，打开一只**已认主且属于自己**的人偶详情。
2. 点击底部 **更换形象**。
3. 在 2 分钟内，在刚才的同一个群或私聊中直接发送一张图片。支持静态 JPG、PNG、WebP，最大 5 MB。
4. 收到“已提交人工审核”后等待管理员处理。2 分钟限制针对发图及提交阶段，人工审核不受这 2 分钟限制。
5. 再打开详情，可以看到待审核状态或驳回原因；通过后图片在详情标题下方显示。
6. 点击 **恢复默认形象** 会移除自定义形象，并撤销该人偶未完成的上传和待审图片。

群内如果没有免 @ 接收能力，机器人可能收不到单独发送的图片。请在私聊重新开始“更换形象”，再发图片；不能在群里开始等待，却跑到私聊直接发图。代码不会改变 QQ 的消息接收权限。

每只人偶同时只能有一张待审图片；每名角色 24 小时内最多提交 10 张。错误格式可在等待有效期内重试。上传等待、取消按钮都校验玩家、会话和本次随机凭据，旧按钮不会取消新上传。

审核结果在玩家下一次打开详情时显示，当前没有另行向群或私聊推送审批结果的机制。

## 7. 第一次测试建议按这个顺序

| 操作 | 应看到的结果 |
| --- | --- |
| 上传正常的卡通机巧图片 | 玩家提示等待人工审核，原形象不变 |
| 在未登录浏览器打开待审预览地址 | 无法查看图片 |
| 管理员填写说明后驳回这张测试图 | 玩家详情显示原因，原形象不变 |
| 再提交另一张合规图片，管理员通过 | 图床上传成功后详情标题下面出现图片 |
| 通过后再次点击同一条旧审核按钮 | 提示已经处理，不重复更新 |
| 点击恢复默认形象 | 自定义图片消失，待审申请撤销 |
| 切换只读观察员账号 | 能查看记录，不能通过或驳回 |

不必为了测试主动上传真实违禁内容；可以用合规测试图填写“流程测试驳回”验证驳回分支。

## 8. 常见问题

| 现象 | 处理方法 |
| --- | --- |
| 提示图床类型无效 | 当前使用 `provider: generic`，不是 `r2` |
| Worker 返回 401 | 检查游戏 `token` 与 Worker Secret `UPLOAD_TOKEN` 是否相同，且没有额外前缀或空格 |
| Worker 返回 503 | 检查 `PORTRAITS` 桶绑定、`PUBLIC_BASE_URL` 和 Secret 是否已部署到当前版本 |
| 浏览器直接打开 Worker /upload 显示 405 | 浏览器是 GET 请求，上传接口只接受 POST；这本身正常 |
| 公共根域名打开报错，但完整图片链接正常 | 应测试根地址加对象路径，如 `/portraits/文件名.webp`，根地址不提供目录列表 |
| 后台有待审图，但通过时报图床上传失败 | 图片仍待审。检查 Worker 配置、令牌、R2 用量和服务器出站网络，再重试；无需让玩家重传 |
| QQ 单独发图没有响应 | 先确认等待是否还有效、会话是否一致；群权限不支持则到私聊重新开始 |
| 详情显示待审核很久 | 管理员尚未处理；系统不会自动批准 |
| 图床 URL 在自己电脑可看，QQ 看不到 | 检查直链是否无需登录即可访问、是否受防盗链或地区网络限制；在 QQ 实测，必要时更换服务 |
| 后台预览提示图片不存在 | 可能已被处理、玩家已撤销，或者 `.data` 本地文件被删；先刷新列表，确认存储目录 |
| 管理后台 Not Found | 本地默认端口是 17118，路径 `/admin`；核对启动日志与后台访问配置，17117 不是该后台 |
| 上传提示超时 | 重新点击更换形象后发送；开始新等待不会让旧凭据重新有效 |

## 9. 部署后的联调顺序与正式切换

1. 完成第 3 节，先确认桶中一张合规测试图的公开地址可访问。
2. 部署 Worker，检查绑定和变量均已生效；单独打开 `/upload` 返回 405 是正常的，不要据此判断上传失败。
3. 填写游戏 `generic` 配置，重新加载；用第 6 节的玩家流程发一张合规图片。
4. 后台通过审核后，确认 R2 桶里出现 `portraits/随机编号.webp` 对象。
5. 确认该对象的完整公开地址能在未登录浏览器显示，再在手机 QQ 里打开机巧详情验证。
6. 测试成功后确定正式图片域名，更新 Worker 的 `PUBLIC_BASE_URL` 并重新部署。该变量只影响之后发布的图片。
7. 如已有 ImgBB 或 r2.dev 图片，旧 URL 仍保存在人偶状态里。没有自动迁移功能；少量测试图可在新域名配置后通过更换形象重新提交。不要提前删除旧图或禁用旧域名。

当前方案上传超时为游戏侧 20 秒；超时后仍可从后台重试。异常时查看 Worker 请求状态和游戏日志，不要输出 `Authorization` 或 Secret。Workers/R2 的额度应在控制台定期检查。

### CORS、防盗链与缓存

游戏服务器向 Worker 上传不受浏览器 CORS 限制，QQ 通过图片 URL 显示也不等于网页脚本跨域读取，不必为此开放任意浏览器跨域上传。图片公开域名应允许正常匿名读取，不要加需要登录、人机验证或只能带特定 Referer 的规则，否则 QQ 可能取不到图。

示例写入一天的对象缓存时间；自定义域名的实际缓存行为以 Cloudflare 配置为准。更换形象会产生新文件名，避免覆盖旧 URL 引发旧图缓存。若误审图片已公开，除处理游戏中正在引用的形象外，还需删除对应 R2 对象并清除自定义域名的 CDN 缓存；已经由客户端缓存的内容无法保证立即撤回。

## 10. 数据保存与维护边界

- 本地压缩文件保存在运行目录的 `.data/automaton-portraits/`，已加入 Git 忽略。不要将它配置成公开静态目录，也不要部署时清空。
- 备份游戏数据库时一起备份该目录。多进程或多机器部署，需要这些进程能够读写同一个受保护目录。
- 通过前只保存本地压缩图；驳回和撤销会清理待审文件；更新或恢复默认会清理被替换的本地图片。
- 审核完成后列表保留文字记录，待审预览接口不再提供该图片。
- 未处理的待审申请不会自动通过或自动过期，应定期在后台清理积压。进程异常退出可能留下没有数据库记录的本地文件，目前没有自动孤立文件清理任务。
- 更换形象不会自动删除 R2 中的旧图片；需在 R2 控制台管理。只清理确认不再被游戏引用的对象。R2 写入成功而游戏数据库提交失败时，可能留下已审核但未使用的远端图片；数据库事务不能回滚 R2。
- 没有配置图床时，可以提交本地待审图片并驳回，但不能通过发布。人工审核无需任何 AI 服务配置。
