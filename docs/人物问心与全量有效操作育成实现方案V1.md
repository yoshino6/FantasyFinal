# 人物问心与全量有效操作育成实现方案 V1

状态：**实现方案；问心已编码，人物行迹正在按服务接入，尚未达到全量覆盖；数据库迁移与上线未验证**。本轮实际交付及缺口见[行迹实装成果](人物行迹基于player_events实装成果20260914.md)。玩法与数值规则见[窥尘起人物问心与行迹育成系统设计 V1](窥尘起人物问心与行迹育成系统设计V1.md)。本文件将用户补充的“人物所有有效操作都能记录”作为覆盖目标；前文列举的委托、任务、NPC、战斗、切磋只是示例，不能作为完整接入范围。

## 1. 交付定义

最终交付须同时具备四件事：①窥尘角色实际升到 Lv.11～Lv.20 时，每级产生一条可选择的问心事件，旧角色幂等补齐该区间的缺失记录；②人物发生的**每一笔有效游戏操作**都能在人物行迹中找到事实记录；③每种有效操作都有确定、可解释的六维倾向规则；④有效行迹按抗刷规则积累，达标后可领取对应六维的质变。不能把“已有某些成就事件”或“只接入几个服务”称作全量覆盖。

这里的“有效操作”是**已提交的业务状态转换或已完成的业务结算**，记录的是发生了什么，不是玩家输入了哪条指令。例如“买入订单实际成交”“委托由未接取变为已接取”“一场战斗以失败结算”分别是一笔事实；玩家可以通过按钮、文本命令或其他入口达成同一事实，记录口径相同。一次指令若因校验失败没有业务结果，就没有事实；一次指令若成功完成多个独立业务结果，则按业务结果分别记。战斗胜利、失败、撤退都可记录为不同结算结果，**不记录每次出手或每个回合**。打开面板、查询信息、按钮填词、数据库回滚、重复回调造成的无变化，不是有效操作。定时器自动恢复、系统刷新、管理员造数、NPC 自行活动要另列系统来源，不冒充人物主动行迹。

**事实记录与育成积分分开**：合格事实必须记录，即使达到每日上限、受到同源衰减、暂未解锁质变，记录仍存在并注明“本次有效积分 0”的原因。六维倾向向量表示行为性质，可与本次实际到账积分不同；不能因不发积分而丢掉操作。非玩家角色及自动生成活动不能给玩家制造有效积分。

## 3. 全量操作分类与六维规则

建立带版本的 `OperationKind` 注册表。每个正式类型必须声明：业务完成条件、参与角色、来源实体及唯一键、顶层或子操作、六维权重向量、积分策略、隐私级别和显示文案。六维顺序固定为**体质、精神、力量、智力、敏捷、感知**，例如 `{0,0,0,2,0,1}`。权重不是直接属性点；实际积分按策略与上限计算。**新写操作未注册类型时不能悄悄跳过记录或借用“通用奖励”倾向**：开发期校验失败，历史／运行期可写 `unmapped` 待映射事实并报警，映射完成后才允许积分结算。

### 顶层事实与子操作

一次业务可能同时改多项状态：例如完成委托会扣物品、发铜币、发经验、推进任务、升级。人物操作列表显示一笔**委托完成结算**，其详情保存奖励与派生变化；不会把每个 SQL 更新、经验到账或库存行变动当成新的玩家操作。若升级又生成独立的问心资格，则通过 `root_event_id` 关联原委托结算和升级结果，不重复领取同一行为积分。买卖须区分挂单成功、订单成交、撤单完成三个真正发生的状态转换；成交以交易 ID 记一次，买卖双方各有自身角色的结果记录。战斗以 session ID 和参与角色为唯一来源，**每场只记最终结算一条**，详情可含伤害、治疗、防护等汇总，不另记开战、回合和出手。

## 4. 数据结构与接口

本轮调整为扩展既有事件表并新增育成余额与变动表，不把全量数据塞进 `characters` JSON 字段：

1. `character_growth_profiles`：`character_id` 主键、出生可塑六维 0.1 单位整数、解锁时初始总和 `initial_birth_total_units≤120`、当前总和 `current_birth_total_units≤120`（也可从六维校验求和）、职业等外源成长来源版本、已结算等级成长六维、版本号。初始总和只供追溯，不能拿它限制大成功后允许增加的当前总和。原 `_growth` 字段在兼容期仍用于旧路径读写，但切换后需明确单一计算来源。
2. `character_question_choices`：`character_id,to_level` 唯一、`from_level,realm_stage,event_code,event_version,options_snapshot_json,status,chosen_option,result_tier_internal,target_gain_units,actual_gain_units,actual_loss_units,old_growth_json,new_growth_json,result_copy_id,result_copy_version,limit_reason,created_at,chosen_at`。内部结果类别只供结算和审计，不输出到结果页；事件与结果文案快照防止更新配置改变旧票。重复确认读取已提交的原结果和原文案，不重新抽 80%／20%。
3. `player_events` 扩展（沿用 `id,player_id,event_type,payload,created_at`）：新增 `character_id,root_event_id,kind_version,source_system,source_id,source_step,source_hash,correlation_id,actor_role,outcome,occurred_at,title,summary,weight_json,raw_points_units,effective_points_units,point_delta_json,score_key,score_reason,mapping_status,business_date`。唯一键为 `(character_id,source_hash)`，哈希输入含角色、来源、阶段和事件类型；战斗固定 `source_id=session_id`，成交固定真实交易 ID，委托接取／完成用委托实例 ID 加不同阶段。长业务 ID 保留原文并参与稳定哈希，不能截断后碰撞。建 `(character_id,occurred_at,id)` 时间分页索引，以及 `(character_id,event_type,occurred_at,id)` 类型筛选索引。已有事件保持兼容；能复用已有事件行的结算不另造重复事件。敏感聊天原文、联系方式、交易对方隐私不入账，只留必要业务 ID 与摘要。
4. `character_tendency_balances` 和 `character_tendency_changes`：前者每角色六维累计、已消费值、版本；后者逐笔记原事实 ID、六维积分变动或质变领取、前后余额、永久六维变动、时间。行迹事实永久可追溯；大表通过归档／分区与索引控制性能，归档不影响角色查询和审计。

服务接口草案：

```ts
recordCharacterOperation(connection, {
  characterId, kind, source: { system, id, step }, rootOperationId,
  outcome, context, actorRole, occurredAt
}) // 业务事务内；返回 factId / duplicate，绝不由前端提供积分

applyOperationTendency(connection, factId) // 从版本化注册表算六维和有效积分，幂等
createQuestionChoicesForLevel(connection, characterId, fromLevel, toLevel)
previewQuestionChoice(connection, characterId, toLevel, optionCode) // 仅返回题目、选项和倾向／排斥方向
confirmQuestionChoice(connection, characterId, toLevel, optionCode, expectedVersion)
claimTendencyMutation(connection, characterId, attribute, expectedVersion)
```

积分、倾向和操作类型由服务端从可信结算结果推导。业务结算成功后同事务插入事实并改余额；唯一键冲突返回已有事实，不再次发分。事务死锁重试沿用 `withTransaction`，但不可用新的随机来源 ID 替代可复用的业务 ID，否则重试会重复记账。面板查询与分页只读，不触发积分。

预留只读查询接口：`listCharacterOperations(characterId, { kind?, outcome?, from?, to?, cursor?, limit? })` 与 `getCharacterOperationDetail(characterId, factId)`。列表按 `occurred_at,id` 游标分页，展示时间、结果、标题、六维倾向、实际积分；详情展示业务来源、对象名称的安全快照、关键数值变化、结算结果、去重／衰减原因和关联的同一业务结果。详情必须用 `character_id` 校验归属，不能凭连续 `factId` 读取别人的记录；管理员审计另走权限入口。记录写入时保存必要快照，避免日后物品改名、任务模板更新或交易对方删号后详情无法解释。

## 5. 问心与属性计算接线

先做只读迁移预演：逐角色解释出生成长、职业成长和其他历史来源，保存旧面板六维、等级、成长及现有装备／祝福／进化结果。不能把当前 `_growth` 总和误当出生预算；缺少可靠来源的历史角色要列出差异，人工确定迁移策略后才能写库。

问心改变出生可塑成长后，立即按最新成长率重算 Lv.1 至当前等级的全部成长份数。普通经验结算、家园休息经验、任务经验、天赋经验、连续升级、进化注射都要调用同一个升级范围判断，并仅在目标等级为 Lv.11～Lv.20 时出票；修复／回退等级的历史维护路径须单列迁移，不伪造问心票。旧角色在打开人物面板、主动打开问心或被普通操作阻断检查时，按当前等级幂等补齐该区间内缺失的票。问心题目以[窥尘问心深层事件题库 V3](窥尘问心深层事件题库V3.md)为运行时内容，结果反馈用[问心选择结果文案 V1](窥尘问心选择结果文案V1.md)。每次仅选择一项倾向维及一项排斥维；普通结果在两维间转移，结算前后总和不变；大成功只增加倾向维，当前出生六维总和不超过 12.0。计算按 0.1 单位整数执行，排斥维可降至 0。角色当前面板、战斗属性和探索判定在选择后同步使用重算结果。

确认选项时，锁角色成长档案和问心票，校验事件版本与未领取状态，先以 80%／20% 判定内部结果类别，再按设计稿计算实际变动，并在同一事务内保存类别、目标值、实际增减、前后快照及本次文案 ID。普通结果即使排斥不足也只转移实际扣掉的量；大成功不能动排斥维。结果页只输出一句模糊文案与**实际发生变化**的方向，例如“智力成长↑，力量成长↓”或仅“智力成长↑”，不输出点数、百分比或类别名；无实际变动时如实提示成长未变。管理员审计保留完整计算明细，用户后续查询详情的开放字段可另行定义。

职业成长现有追溯语义须保持在独立外源层；若后续决定改为非追溯，属于另一次数值改动，不与本系统混在一起。质变的永久基础属性要在 `character.service.ts` 的统一六维构建处进入面板和战斗，同事务重算缓存，不修改出生可塑成长。

## 6. 积分策略、反刷与质变

每个正式 `OperationKind` 要有六维向量和积分策略。V1 可沿用设计稿的“合格高价值成果 3 点、某维 100 点兑换基础六维 +1”作为**建议试算值**，但全量操作覆盖后需按真实行为频率重新校准。换装完成、撤单完成、休息结算、购买成交等有效结果虽记事实，却不应和完成委托拿同样积分：推荐按 `0/微量/普通/重要` 四档配置，并对微量积分采用整数子单位累计；每笔写清 `raw_points` 与因日限额／同源衰减后的 `effective_points`。积分为 0 的事实仍保存六维倾向向量和原因。

反刷按**来源、目标、时间、结果**组合设计：同一任务阶段只计一次，同一个副本／战斗 session 单独核算，同一对手短时重复切磋衰减；买卖互刷、装备反复穿脱、家园反复进出、NPC 重复闲聊、往返抵达、撤单重挂、赠礼退回不能生成无限积分。组队贡献按本人实际参与和结算，不能只要人在队伍里就获得全部行为分。每日／每周限额用 Asia/Shanghai 业务日期，并在事务中原子更新；上限后的事实照记。

质变领取用角色行锁、余额条件更新和唯一领取序号保证一次性。若尚未确定每维／每周／终身上限，先只开放积分记录与展示，不开放无限兑换；阈值和限制经数值回放确认后再开。领取后该维基础六维 +1，成长 `g`、职业成长 `p`、出生预算 `S` 保持不变。
